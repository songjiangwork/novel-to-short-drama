### Semantic-round decision gate

The frozen policy says one proposal plus at most one regeneration, and the CLI states a two-round maximum for a new window; neither explicitly grants a fresh budget after an unresolved claim. The implementation enforces two **per invocation**, because a window normally has one invocation and claims cannot be reclaimed. Thus the architecture does **not** establish that the ceiling resets per attempt. Treat the ceiling as applying across the entire window execution lineage unless an explicit architecture decision amends that policy. Unknown counts must be treated as potentially exhausted, not zero. For this incident the prior count is unknown, so **no new dispatch is permitted under the existing ceiling**. An approved exception or revised policy, including its maximum semantic and technical budget and accounting semantics, is a prerequisite to any implementation or authorization. Operator acknowledgment alone cannot grant that exception. The record schemas below describe the mechanism conditional on that decision; they do not authorize it.

## State machine

All transitions that could authorize dispatch occur under the same story execution guard, with fresh authority and root checks. States are derived from verified immutable records, not an editable status flag.

```text
CLAIMED_UNRESOLVED + checkpoint absent
  -> DECIDED        (durable, unique decision; policy gate satisfied)
  -> CONSUMED       (durable single-use attempt intent, before dispatch)
  -> CHECKPOINTED   (normal verified checkpoint; lineage link recorded)
  -> FAILED         (durable terminal result, checkpoint absent)
  -> OUTCOME_UNKNOWN (consumption exists, no trustworthy terminal result)

Any state + verified checkpoint -> VERIFIED_REUSE (takes precedence; zero dispatch)
No verified checkpoint + invalid/conflicting/ambiguous evidence -> BLOCKED (zero dispatch)
```

A decision without consumption can be consumed once only after all checks are repeated. Once consumed, it can never authorize another invocation, including after a crash before the first network call. `FAILED` and `OUTCOME_UNKNOWN` both prohibit additional recovery by default. A failure to persist a terminal record leaves `OUTCOME_UNKNOWN`; absence of a terminal record never proves no dispatch. No timeout, stale lock, restart, or operator identity creates a new authorization. A new architecture decision and separately reviewed protocol would be needed for any further attempt; this v1 provides no override.

## Proposed v1 records

Use strict canonical JSON, bounded sizes, closed field sets, SHA-256 `content_hash` of the canonical object excluding its own identity, and exact round-trip verification. Reject unknown versions, duplicate keys, noncanonical bytes, bad hashes, symlinks, unsafe files and inconsistent references. Names are deterministic from the original claim identity and record type in the **existing execution root**; at most one decision, one consumption and one terminal record per claim. A no-clobber fixed slot prevents competing decision IDs from creating parallel authorizations. Record IDs are content identities; timestamps are UTC audit metadata, never expiry or proof of ordering. No source text, responses, credentials or exception messages belong in these records.

* **Decision v1**: `schema_version`, `record_type`, `decision_identity`; unique `decision_id`; `operator_id`, `decided_at`, bounded `reason`, evidence references/digests (including forensics and any independently verified observations), explicit `prior_outcome: unknown`, `ack_prior_requests_may_have_completed: true`, `ack_duplicate_generation_possible: true`; `claim_identity` and SHA-256 of the exact canonical claim bytes; `preparation_identity`, window ID/ordinal, `request_identity` and semantic request hash; full source snapshot and hash identifying A5/A6 refs/revisions/hashes and CURRENT authority, B1.2 strategy ref/hash and selection mode plus CURRENT pointer ref if applicable; canonical execution, checkpoint, artifact and pointer root paths and device/inode identities; policy-decision reference and approved caps; exactly one `attempt_id`. Values must match a freshly rebuilt trusted session and original claim; a signed policy decision is not inferred from the operator's data.
* **Consumption/attempt intent v1**: `schema_version`, `record_type`, `consumption_identity`, decision identity and ID, claim identity and claim-byte hash, same attempt ID, `consumed_at`, and digest of the exact revalidated authority/root/session bindings and budget. Its durable publication is the irreversible single-use point, before any Provider dispatch. It says **may have dispatched**, never that dispatch occurred.
* **Terminal v1**: `schema_version`, `record_type`, `terminal_identity`, decision and consumption identities, attempt ID, `recorded_at`, outcome `CHECKPOINTED` or `FAILED`, bounded safe failure code or null, trusted observed counts or null, and for `CHECKPOINTED` the exact checkpoint identity and SHA-256 of canonical checkpoint bytes. Unknown counts remain null, not zero. `FAILED` is permitted only after a fresh verified checkpoint-absence check; if anything is uncertain, omit terminal and leave outcome unknown. A valid checkpoint found later wins over an earlier failure record, which remains immutable as historical evidence.

The exact root identity is the canonical path and `(st_dev, st_ino, file type)` of each opened root, validated against the trusted parents and disjoint protected trees. Capture and compare all four roots at decision and consumption; an absent or replaced root fails closed. Keep the same root instances while guarded. Artifact refs, source snapshot, strategy selection and request must be checked structurally and through existing authority verification, not only by comparing hashes. Record the relevant A5/A6 CURRENT references and B1.2 CURRENT selection when applicable; re-resolve them before dispatch and checkpoint. Runtime/tokenizer freshness and budgets must be re-established as for the normal runner; runtime-only settings remain distinct from semantic identity.

## Atomic persistence and crash consistency

Reuse the existing private root, directory-descriptor/no-follow, stable-file and inode checks, bounded strict reads, exclusive flock and same-directory temporary-file, file-fsync, no-clobber hard-link and directory-fsync pattern used by claims/checkpoints. Add a narrowly scoped record codec/store; do not rename, rewrite, delete, or reset the original claim or checkpoint. Create only new recovery files in the execution root. Before success, check ownership/mode, root identity and exact canonical bytes; fsync a newly created root's parent if creation is ever allowed. For this incident require both roots already exist.

Write and fsync the complete private temporary file, link it to its fixed final name without replacement, then fsync the directory and verify the exact final record. Dispatch is forbidden unless **both** decision and consumption have completed these steps successfully in the current guarded operation. Existing identical decision evidence may be read for inspection; it never overrides a consumption. Conflicting, malformed or partial fixed-slot evidence blocks. Any write, link, verification or fsync failure stops without dispatch; if a link may have succeeded, its existence or durability is uncertain and must not be treated as absent. Crash leftovers and uncertain durability require read-only investigation, not automatic cleanup or reauthorization. A durable consumption discovered on restart is spent regardless of whether dispatch occurred; if its durability is uncertain, block as well. Temporary files are never authority; suspicious remnants or inability to establish a clean state block, and their disposition requires separate review. Do not rely on atomicity across files: decision precedes consumption; consumption precedes dispatch; checkpoint precedes terminal. Each stage must stand safely alone.

On success use the existing `save_checkpoint` and verify its exact bytes by normal loading while holding the guard, then publish the terminal link. If checkpoint publication or directory fsync has an uncertain outcome, stop and inspect on a later invocation; verified checkpoint takes precedence. A terminal write failure cannot invalidate a checkpoint or authorize another attempt. The sidecar can be completed only from verified, uniquely bound evidence under guard, without Provider calls; otherwise flag an audit gap. No deletion of evidence to resolve a conflict.

## Operator authorization sequence

1. Obtain an explicit architecture decision resolving the lineage-wide round ceiling and a narrowly bounded exception if needed. Without it, stop. Review forensics and exact claim bytes, checkpoint absence, trusted roots and authority; do not interpret server task matches as accepted responses or known counts.
2. Identify the operator, reason and evidence; explicitly acknowledge both possible prior completion and duplicate generation. Display the exact window, claim-byte hash, request, authority, roots, approved budget and policy reference. This is a proposed retry decision only, not semantic or publication approval.
3. Acquire the **existing** exclusive execution guard and hold it through decision, consumption, execution and checkpoint/terminal persistence. Freshly rebuild the complete preparation and request, revalidate A5/A6 CURRENT, B1.2 selection, all root identities and disjointness, pinned prompt/profile/schema, runtime, tokenizer and budgets. Verify exact original canonical claim bytes. Run normal resume verification: a verified checkpoint immediately yields reuse; invalid checkpoint or claim blocks. Inspect all fixed recovery slots; conflict, consumption, terminal, unknown evidence or changed bindings blocks.
4. Publish and durably verify the one decision. Repeat guard/root, claim, checkpoint, authority, request, budget and recovery-slot checks immediately before consuming. If any changed, stop; no decision can be repurposed for another identity. Publish and durably verify the single consumption. Recheck guard, authority and checkpoint before dispatch; failure after consumption spends the attempt and stops.
5. Only if the separate policy decision permits it, invoke one bounded attempt with normal runtime, provenance, schema and semantic checks and technical limits. Revalidate authority after responses and before acceptance; hold guard through the normal checkpoint save and verification. No regular runner path may invoke this exception. A normal runner still rejects every unresolved or invalid claim for every missing window, even if a decision exists.
6. Write the terminal record after verified checkpoint or safely observed failure; if terminal persistence fails, report unknown and stop. On later inspection check checkpoint first. Additional recovery is prohibited by v1. Independently perform reconciliation, whole-plan validation, human review and publication approval under their existing contracts; none follows from retry authorization or local semantic acceptance.

## Checkpoint and proposal provenance

The v1 checkpoint filename and identity remain derived by the existing codec from the same preparation/window/request and accepted payload; a recovery ID is **not** substituted into either. The accepted proposal must retain the actual recovery invocation's provenance and internally consistent round/rejected-round/provider-attempt evidence. Prior unknown counts cannot be invented or included as zero. Existing v1 accounting is invocation-local in practice, despite comments describing window totals; it cannot represent an unknown earlier lineage. Therefore review must decide whether v1 checkpoint reuse with explicitly attempt-local counters and a mandatory audit sidecar is acceptable, or a future versioned checkpoint/accounting contract is required. Do not implement by silently relabeling lineage totals. A terminal link binds decision -> consumption -> checkpoint identity and byte hash; it adds lineage without mutating the checkpoint. Existing readers do not enforce that link, so operators must be told about an incomplete sidecar and any downstream audit requirement must be explicitly implemented and reviewed. Verified checkpoint reuse still takes precedence over recovery authorization, including when the link is missing or invalid; an audit gap is not permission to generate.

## Failure-mode matrix

| Condition | Required result |
| --- | --- |
| Verified checkpoint before decision, consumption, or dispatch; including after uncertain save | Reuse verified checkpoint; no dispatch; retain all records. |
| Malformed, conflicting or noncanonical claim/checkpoint/record; root or authority mismatch | Block; no dispatch; preserve evidence. |
| Decision write/link/fsync fails or crashes | No dispatch; uncertain final slot blocks automatic continuation. |
| Consumption write/link/fsync fails or crashes | No dispatch in that process; present or uncertain consumption is spent/blocked, never retried. |
| Crash after consumption, before/during/after Provider call | Outcome unknown, even if no call actually happened; no further dispatch. |
| Provider/parse/provenance/semantic/authority failure after consumption | Stop; record safe failure only if checkpoint absence and evidence are verifiable; otherwise unknown. Counts may be null. |
| Accepted response but checkpoint save/link/fsync fails | Stop; inspect exact checkpoint later; verified checkpoint wins, absent/uncertain remains spent and unknown or safely recorded failure. |
| Checkpoint durable but terminal write fails | Reuse checkpoint, flag audit gap, no dispatch; reconstruct only if unique verified evidence permits. |
| Two operators or a normal runner race | One guard serializes cooperating processes; fixed no-clobber slots reject competing decisions; later process rechecks checkpoint and consumption. |
| A5/A6/B1.2 authority or root changes at any revalidation | Block; if consumed, attempt remains spent; never move records to a new identity. |

## Threat and concurrency boundary

The protocol assumes trusted operator-owned stable parents, private roots, reliable local flock/hard links/fsync and cooperating executors using the same roots. The advisory lock cannot constrain non-cooperating processes, other roots, privileged modification, hostile mounts or a lying filesystem; these are outside the existing primitive's guarantee and require operational controls. Hashes detect mismatched bytes, not malicious edits by a root owner; operator identity is an audit assertion unless a separately specified authentication system verifies it. Guard and no-clobber slots prevent two cooperating operators from consuming once each, not duplicate requests already sent by the Provider or technical retries inside the one permitted attempt. Authority may change in another subsystem despite the lock; existing before/after authority checks prevent acceptance on observed change, not Provider-side cancellation. A verified checkpoint is authoritative only after the existing session and authority verification succeeds; invalid evidence is never treated as absence.

## Fake-client test plan for a future implementation

All tests use isolated temporary trusted roots, controlled fake clients, simulated authority stores and no network. Assert original claim bytes and path remain identical throughout, checkpoint is untouched on every blocked path, and no CURRENT or publication writes occur.

* Exercise exact session, claim and root bindings; altered A5/A6 refs/CURRENT, B1.2 ref/hash/pointer or selection mode, request/prompt/schema, preparation, root path/inode, symlink and ownership each cause zero calls. Rebuild and check freshness, limits and both request budgets.
* Verify decision acknowledgments, policy gate, strict canonical schemas, hashes, closed fields, duplicate keys, fixed slots and conflicting operators. Unknown prior rounds block Alice without an explicit approved policy exception; prove neither evidence references nor operator acknowledgment grant one.
* Inject failures and crashes at each temp write, file fsync, link, directory fsync, verification, after decision, after consumption, immediately before dispatch, each fake response, checkpoint publication and terminal write. Restart and assert no second dispatch after consumption or ambiguous durability, including a crash before the first call; no partial file becomes authority.
* Race cooperating operators and the normal runner under the same guard. Assert at most one consumption and one recovery invocation, all missing unresolved claims still block the regular runner, and verified checkpoint wins at every inspection boundary. Test invalid/conflicting checkpoint as a block, not a miss.
* Fake valid proposals, semantic rejection, malformed/schema/provenance failures, technical exhaustion, authority changes during a response, and accepted response with checkpoint failure. Verify bounded attempts, exact invocation provenance, null unknown counts, terminal failure or unknown as appropriate, no automatic third attempt, and no invented prior counts. Verify v1 checkpoint round-trip, deterministic path, byte identity and sidecar binding, including checkpoint-without-sidecar reuse plus audit gap.
* Test concurrent checkpoint appearance and conflicting terminal evidence, root replacement and unsupported filesystem operations. Confirm non-cooperating-process limitations are documented rather than claimed as tested guarantees.

## Decisions required before implementation

1. Does the frozen two-round limit apply to the entire lineage? This proposal treats it as lineage-wide and the incident as potentially exhausted. If an exception is desired, who can amend it, what exact additional semantic and technical budget is allowed, and how is that policy decision recorded and authenticated?
2. Can existing v1 checkpoint counters be explicitly scoped to the recovered invocation, given unknown prior counts and the current window-total wording, or is a new checkpoint/accounting version required? How will downstream consumers surface and enforce the sidecar audit gap without undermining verified-checkpoint precedence?
3. What operator authentication, policy-decision authentication and evidence-retention standard is required beyond local filesystem trust? What exact safe failure codes and maximum record sizes should be standardized?
4. Which audited procedure, outside v1, handles corrupt or uncertain artifacts and any request for further recovery? It must not silently delete or replace the claim, checkpoint or recovery records. No such procedure is authorized here.
