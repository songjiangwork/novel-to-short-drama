# B5.7 — Release Variant Review + Approval Gate

状态：**FROZEN**

## 1. 职责

B5.7 是 B5 唯一正式 human approval gate。

它不判断 generated media quality，而是决定：

```text
这个 exact EpisodeReleaseVariant
是否被授权成为 downstream
Asset Resolution / Execution Compilation
的正式 release semantic authority？
```

正式输出：

```text
ReleaseVariantApprovalRecord
```

## 2. Approval target

B5.7 批准 exact：

```text
EpisodeReleaseVariant
  id
  revision
  content_hash
```

并必须 exact pin：

```text
ReleaseVariantValidationReport
  id
  revision
  hash

validated_release_variant_bundle_hash

source EpisodeShotPlan
  id
  revision
  hash
  ShotPlanApprovalRecord
```

Approval 是对 immutable exact content 的授权，不是对“英文竖屏版”等模糊概念的授权。

## 3. Approval scope

B5 与 B4 的重要区别：同一 episode 可以同时存在多个 approved release variants。

正式 scope：

```text
ApprovalScope
=
episode_id
+
ReleaseVariantIdentity
```

约束：

```text
one ApprovalScope
→ at most one current APPROVED revision
```

不同 ReleaseVariantIdentity 互不 supersede。

例如同一 E01 可以同时 current APPROVED：

```text
zh-CN / 9:16
en-US / 9:16
zh-CN / 16:9
en-US / 16:9
```

## 4. Entry gate

正式 review/approval 前必须满足：

```text
EpisodeReleaseVariant.lifecycle_status == DRAFT

B5.5 result ∈ {
  PASS,
  PASS_WITH_REVIEW_ITEMS
}

EpisodeReleaseVariant.content_hash unchanged
source_validated_release_variant_bundle_hash matches report
source EpisodeShotPlan lineage valid/current for normal approval
all exact refs/hashes resolve
all REVIEW_REQUIRED items can be identified
```

`FAIL` 不得批准。

## 5. Formal decision

正式 decision：

```text
APPROVE
REVISION_REQUESTED
ABANDON
```

不引入：

```text
PARTIAL_APPROVE
CONDITIONAL_APPROVE
TEMPORARY_APPROVE
SOFT_APPROVE
```

避免模糊 downstream authority。

## 6. APPROVE

只有以下条件全部成立才允许：

```text
exact target hash verified
exact validation report verified
validated bundle hash verified
source ShotPlan lineage eligible
all REVIEW_REQUIRED items formally disposed
no disposition requests revision
```

成功后：

```text
EpisodeReleaseVariant.lifecycle_status
DRAFT → APPROVED
```

并形成 downstream authorization：

```text
APPROVED EpisodeReleaseVariant
+
ReleaseVariantApprovalRecord
```

## 7. REVISION_REQUESTED

如果 reviewer 认为任何 release semantic realization 必须改变，例如：

- localization
- character voice
- framing
- aspect-ratio adaptation
- subtitle text/timing
- release timing
- audio semantic realization

则 decision：

```text
REVISION_REQUESTED
```

当前 EpisodeReleaseVariant revision 不得 APPROVE。

Reviewer 不在 gate 中直接编辑 canonical artifact；必须 route 到 owning stage，形成 new constituent revision，再重新 B5.5 → B5.6 → B5.7。

## 8. ABANDON

`ABANDON` 表示该 exact revision / variant effort 被明确停止继续作为 active approval candidate。

它不同于：

```text
SUPERSEDED
```

SUPERSEDED 表示有更晚 approved replacement；ABANDONED 表示明确放弃。

Historical lineage 仍保留。

## 9. REVIEW_REQUIRED disposition

如果 B5.5：

```text
PASS_WITH_REVIEW_ITEMS
```

每个 REVIEW_REQUIRED finding 必须 exactly one formal disposition：

```text
ACCEPT_AS_DESIGNED
REVISION_REQUESTED
```

`ACCEPT_AS_DESIGNED` 表示 human 已查看 finding，并判断当前 realization 仍处于 canonical semantic envelope 内；不表示 finding “不存在”。

只要任一 disposition：

```text
REVISION_REQUESTED
```

则 current revision 不得 APPROVE。

WARNING 默认 informational，不要求逐条 disposition，但 reviewer 可以主动据此请求 revision。

## 10. PASS 不等于 approval

正式保持：

```text
B5.5 PASS
≠
B5.7 APPROVE
```

Human reviewer 可以发现 automated validation 未发现的 tone/semantic/release issue，并请求 revision。

Validation 与 approval 必须分层。

## 11. Reviewer authority boundary

Reviewer 可以：

- APPROVE
- REVISION_REQUESTED
- ABANDON
- disposition REVIEW_REQUIRED
- raise HumanReviewFinding
- route requested revision

Reviewer 不能在 B5.7 中直接：

- 改 localized text
- 改 subtitle cue
- 改 framing
- 改 timing
- 改 EpisodeShotPlan

```text
approval gate ≠ editor
```

## 12. Repair routing

Approval record 可以记录：

```text
requested_revision_routes[]
```

典型 authority：

```text
B5_1_CONTEXT_REVISION
B5_2_LOCALIZATION_REFINEMENT
B5_3_FRAMING_REFINEMENT
B5_4_TIMING_REFINEMENT
REQUIRES_B4_REVISION
REQUIRES_B3_REVISION
REQUIRES_EARLIER_UPSTREAM_REVISION
```

Gate 只记录/route，不执行 repair。

## 13. ReleaseVariantApprovalRecord

建议至少包含：

```text
ReleaseVariantApprovalRecord
{
  approval_record_id

  approval_scope {
    episode_id
    release_variant_identity
  }

  episode_release_variant_ref {
    id
    revision
    content_hash
  }

  source_validation_report_ref {
    id
    revision
    hash
  }

  validated_release_variant_bundle_hash

  source_episode_shot_plan_ref {
    id
    revision
    hash
    approval_record_id
  }

  decision
  review_item_dispositions[]
  reviewer_notes
  decision_timestamp
  supersedes_approval_record_ref?
}
```

ApprovalRecord 本身 immutable。

## 14. Hash / validation recheck at approval time

在真正 APPROVE 的瞬间必须重新确认：

```text
current EpisodeReleaseVariant.content_hash
== approval target hash
```

以及：

```text
EpisodeReleaseVariant.source_validated_release_variant_bundle_hash
==
ReleaseVariantValidationReport.validated_release_variant_bundle_hash
```

任何 mismatch：

```text
APPROVAL_BLOCKED
```

Validation 后哪怕只改一个 subtitle 字符，也必须重新 B5.5/B5.6。

## 15. Source EpisodeShotPlan lineage eligibility

Approval 时必须重新检查 source EpisodeShotPlan lineage。

如果 B5 从 ShotPlan rev3 构建，但 approval 前 rev4 已成为 current APPROVED replacement，则 normal workflow 应：

```text
SOURCE_SHOT_PLAN_LINEAGE_STALE
APPROVAL_BLOCKED
```

重新 derive current B5 lineage。

B5.7 不把 stale source silent repin 到新 ShotPlan。

## 16. Historical approval vs current eligibility

若一个 EpisodeReleaseVariant 已在过去正式 APPROVED，后来 source ShotPlan 被新 revision supersede：

- old approval 仍是历史事实；
- old ERV/ApprovalRecord 不 retroactively rewrite；
- normal new execution eligibility 可以变为 stale/ineligible；
- historical reproduction policy 可以后独立设计。

因此必须区分：

```text
historical approval validity
≠
current execution eligibility
```

## 17. Source-lineage eligibility

可以通过 derived governance state 表达：

```text
source_lineage_eligibility
= CURRENT / STALE
```

它不修改 historical EpisodeReleaseVariant content hash，也不篡改过去 approval decision。

Normal new execution 至少要求：

```text
EpisodeReleaseVariant.lifecycle_status == APPROVED
AND
source_lineage_eligibility == CURRENT
```

## 18. Supersession

同一个 ApprovalScope 中，如果：

```text
rev2 APPROVED
rev3 DRAFT
```

rev2 继续是 current APPROVED，直到 rev3 成功 APPROVE。

rev3 APPROVE 时原子性：

```text
rev2 → SUPERSEDED
rev3 → APPROVED
```

不能在 rev3 DRAFT / review 阶段提前 supersede rev2。

历史 ApprovalRecords 永久保留。

## 19. Approval granularity

B5.7 使用：

```text
per episode
per ReleaseVariantIdentity
whole-artifact atomic approval
```

不支持正式：

- PlannedShot-level partial approval
- dialogue-only approval
- framing-only approval
- timing-only approval

Review UI 可以记录逐 Shot reviewed state，但 downstream formal authorization 仍针对完整 exact EpisodeReleaseVariant revision。

## 20. Component artifacts 不是 formal downstream approval object

B5.2/B5.3/B5.4 可以有 validation/review metadata，但不能成为类似：

```text
B5.2 APPROVED
B5.3 APPROVED
```

的独立 downstream authority。

正式 release approval object 只有：

```text
EpisodeReleaseVariant
```

## 21. ReleaseVariantReviewPackage

B5.6 可以 deterministic derive：

```text
ReleaseVariantReviewPackage
```

供 human review，建议包括：

- ReleaseVariantIdentity / target profile
- source ShotPlan summary
- Shot-by-Shot canonical purpose/PCR
- source vs localized dialogue
- framing realization
- release timing
- subtitle realization
- review-required findings
- warnings
- provenance refs

ReviewPackage 不是 approval object；正式批准始终绑定 EpisodeReleaseVariant id/revision/hash。

## 22. Qwen review assistance

Qwen 可以：

- explain localization differences
- summarize framing/timing differences
- explain findings
- compare revisions
- trace provenance

Qwen 不得：

- generate formal approval decision
- disposition REVIEW_REQUIRED on behalf of human
- repair canonical artifact inside approval gate

```text
Qwen may advise; human approves.
```

## 23. Approval / asset boundary

B5.7 APPROVE 不批准：

- concrete character/location image
- concrete WAV/TTS waveform
- LoRA/embedding
- specific voice model
- Picture refs

这些属于 Asset Resolution。

## 24. Approval / execution boundary

B5.7 APPROVE 不批准：

- ProductionShot concrete segmentation
- prompt wording
- H3/ComfyUI workflow
- seed/sampler
- backend clip duration
- encoder implementation

这些属于 downstream execution compilation/backend realization。

## 25. Subtitle/render boundary

B5 批准的是 subtitle semantic text/cue/timing/safe-area intent。

以下通常是 render-only：

- font rasterization
- exact outline width
- encoder output resolution
- codec/container

但 subtitle wording/cue semantics/timing change 不是 render-only，必须 new B5 revision + revalidation/reapproval。

## 26. Spoken timing / concrete audio boundary

B5 批准 release timing semantic realization/tolerance，不批准具体 waveform sample count。

Concrete audio measured duration 只要满足 approved B5 constraints，无需重新 B5 approval；如果无法满足，则产生 downstream asset/execution conflict，不能 silent 扩大 approved timing。

## 27. Downstream exact pinning

正式下游至少必须 pin：

```text
episode_release_variant_id
revision
hash
release_variant_approval_record_id
```

禁止 canonical downstream lineage 使用：

```text
latest approved en-US 9:16
```

Human-friendly selector 只能在 job/artifact 创建前解析；创建后必须 exact pin。

## 28. Approval 与 validation lineage

ApprovalRecord 必须保存 exact ValidationReport ref，使未来可以回答：

- 当时验证了哪个 bundle？
- 有哪些 REVIEW_REQUIRED / WARNING？
- reviewer 如何 disposition？
- 为什么批准/请求 revision？

不能拿另一个 ERV revision 的 ValidationReport 批准当前 revision。

## 29. Validation policy evolution

B5.5 validator contract 后续升级不 retroactively invalidate historical approval，除非未来另有显式 migration/revalidation policy。

Historical approval 永远绑定当时 exact ValidationReport/policy provenance。

## 30. Release profile / terminology updates

Platform safe-area profile 或 LocalizationTerminologyRegistry 后续新 revision 不 retroactively rewrite 已批准 ERV。

如果 current release 要采用新 profile/terminology并影响 semantic realization：

```text
new B5 constituent revision
→ B5.5
→ B5.6
→ B5.7
```

## 31. Cross-episode dependency

默认不强制 Episode N ReleaseVariant 依赖 Episode N-1 ReleaseVariant。

Series-scoped terminology consistency优先通过 pinned shared registry 处理，不建立无意义 episode chain。

只有明确存在 cross-episode release-specific continuity dependency 时，才声明并 pin exact predecessor EpisodeReleaseVariant id/revision/hash/approval record。

## 32. Re-review after change

任何 semantic constituent change 后：

```text
new constituent revision
→ new B5.5 integrated validation
→ new B5.6 EpisodeReleaseVariant revision
→ new B5.7 review
```

禁止“修完后沿用旧 B5.5 直接 approve”。

## 33. Lifecycle behavior

正常：

```text
DRAFT
↓ APPROVE
APPROVED
```

Replacement：

```text
rev2 APPROVED
rev3 DRAFT
↓ APPROVE
rev2 SUPERSEDED
rev3 APPROVED
```

Abandon candidate：

```text
DRAFT
↓ ABANDON
ABANDONED
```

`REVISION_REQUESTED` 是 approval decision，不要求扩张 artifact lifecycle enum；semantic change 通常创建 new revision。

## 34. Reviewer notes

Reviewer notes 属于 governance/audit metadata，不进入 EpisodeReleaseVariant semantic content hash。

它们应进入 `ReleaseVariantApprovalRecord` 自身 audit trail。

## 35. Formal review completeness

APPROVE 前 Python 必须 deterministic 检查：

- all REVIEW_REQUIRED finding IDs covered
- exactly one disposition per finding
- no conflicting duplicate disposition
- no disposition = REVISION_REQUESTED
- target hash/report/bundle hash exact
- approval scope uniqueness
- source lineage eligibility

## 36. Python / Human / Qwen

Python：

- exact target hash verification
- validation report match
- bundle hash match
- review-item completeness
- approval-scope uniqueness
- lifecycle transition
- supersession
- source-lineage eligibility
- provenance / audit recording

Human：

- APPROVE / REVISION_REQUESTED / ABANDON
- REVIEW_REQUIRED dispositions
- HumanReviewFinding

Qwen：

- explain / compare / summarize / trace

Qwen 不能 self-approve。

## 37. Generated media boundary

保持全 pipeline 状态纪律：

```text
semantic artifact
→ APPROVED

generated media
→ ACCEPTED / REJECTED / RETRY
```

因此：

```text
EpisodeReleaseVariant APPROVED
≠ generated video ACCEPTED
```

## 38. 冻结原则

1. B5.7 是 B5 唯一 formal human approval gate。
2. 正式 artifact 为 immutable `ReleaseVariantApprovalRecord`。
3. Approval target 是 exact EpisodeReleaseVariant id/revision/content_hash。
4. Approval scope = episode_id + ReleaseVariantIdentity。
5. 一个 episode 可同时存在多个不同 ReleaseVariantIdentity 的 approved variants。
6. 同一 ApprovalScope 最多一个 current APPROVED revision。
7. Decision = APPROVE / REVISION_REQUESTED / ABANDON。
8. B5.5 PASS/PASS_WITH_REVIEW_ITEMS 不等于自动 APPROVE。
9. 所有 REVIEW_REQUIRED 必须 formal `ACCEPT_AS_DESIGNED` / `REVISION_REQUESTED`。
10. 任一 REVISION_REQUESTED 阻止当前 revision APPROVE。
11. Reviewer 不直接编辑 canonical artifact；semantic change route 到 owning stage。
12. 任一 constituent semantic change 都必须重新 B5.5 → B5.6 → B5.7。
13. Approval 前重新验证 target hash / report / validated bundle hash。
14. Source EpisodeShotPlan lineage 在 normal approval 时必须 eligible/current。
15. Historical approval 不因后续 upstream revision retroactively erase。
16. Historical approval 与 current execution eligibility 分离。
17. Normal new execution 只消费 APPROVED + current-lineage EpisodeReleaseVariant。
18. Replacement revision 仅成功 APPROVE 时 atomically supersede 旧 current revision。
19. Approval per-episode/per-variant whole-artifact atomic，不支持 formal per-shot/component partial approval。
20. ReviewPackage 是 derived presentation，不是 approval object。
21. Qwen 可辅助 review，但不能 self-approve。
22. Python 负责 hash/ref/state/scope/disposition completeness/supersession。
23. B5 approval 不批准 concrete assets、TTS waveform、ProductionShot、H3/ComfyUI execution。
24. EpisodeReleaseVariant APPROVED 不等于 generated media ACCEPTED。
25. Downstream 必须 pin exact EpisodeReleaseVariant revision/hash/ApprovalRecord，禁止 implicit latest。
