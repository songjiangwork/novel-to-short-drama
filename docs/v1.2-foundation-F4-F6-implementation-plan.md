## 2. 已冻结语义

### 2.1 Historical validity 与 current eligibility 分离

核心 invariant：

```text
historically valid
!=
currently eligible for ordinary downstream use
```

旧 revision 被 supersede 后：

- immutable artifact 仍然存在；
- exact ArtifactRef 仍然可以 resolve；
- historical approval/provenance 仍然成立；
- 但普通新 downstream work 不再默认把它作为 current authority。

这为未来 B7 提供：

```text
NORMAL_COMPILE
= exact approved + current lineage

REPLAY_COMPILE
= explicit historical exact lineage
```

Issue #2 不实现 B7 execution mode，只实现足够表达和验证上述区别的 generic primitives。

### 2.2 Validation taxonomy

冻结 severity：

```text
BLOCKING
REVIEW_REQUIRED
WARNING
```

冻结 overall result：

```text
FAIL
PASS_WITH_REVIEW_ITEMS
PASS
```

推导规则：

```text
>= 1 BLOCKING
→ FAIL

0 BLOCKING + >= 1 REVIEW_REQUIRED
→ PASS_WITH_REVIEW_ITEMS

0 BLOCKING + 0 REVIEW_REQUIRED
→ PASS
```

`PASS != APPROVED`。

### 2.3 Approval taxonomy

冻结 formal decision：

```text
APPROVE
REVISION_REQUESTED
ABANDON
```

不得使用含义模糊的 generic `REJECT` 替代。

冻结 REVIEW_REQUIRED disposition：

```text
ACCEPT_AS_DESIGNED
REVISION_REQUESTED
```

语义 artifact approval 与 generated-media QC 必须继续分离；现有 v1.1 QC 的：

```text
approve / retry / reject
APPROVED / RETRY_REQUIRED / MANUAL_INTERVENTION
```

不得迁入或复用为 F6 approval states。

## 4. F4 — Lineage

### 4.1 LineageRef

Foundation 提供一个 reusable `LineageRef`，最小语义：

```text
LineageRef {
  role
  artifact_ref: ArtifactRef
}
```

规则：

1. `artifact_ref` 必须使用 Issue #1 canonical `ArtifactRef`。
2. `role` 用于说明这个 upstream ref 在当前 artifact 中的 lineage role。
3. Foundation 不定义 A/B stage-specific role enum；role taxonomy 由 owning stage 定义。
4. Lineage resolution 必须调用 exact `FileArtifactStore.get_ref()` 或等价 exact-ref resolver。
5. logical ID / pathname / implicit latest 都不能替代 ArtifactRef。

Foundation 可以提供：

```text
resolve_lineage_ref(...)
verify_lineage_refs(...)
```

但不得加入 A1/B7-specific logic。

---

## 5. F4 — CurrentPointer

### 5.1 CurrentPointer 是 immutable snapshot

不要把 current pointer 本身实现为一个被反复原地改写的 domain record。

每次 pointer transition 产生新的 immutable `CurrentPointer` snapshot，并通过 `ImmutableArtifactEnvelope` 存入 `FileArtifactStore`。

建议 payload：

```text
CurrentPointer {
  pointer_id
  pointer_kind
  target_ref: ArtifactRef
  authority_ref: ArtifactRef | null
  previous_pointer_ref: ArtifactRef | null
}
```

冻结两种 Foundation-level pointer kind：

```text
CURRENT
CURRENT_APPROVED
```

语义：

```text
CURRENT
→ target_ref 是普通 current artifact
→ authority_ref 必须为空

CURRENT_APPROVED
→ target_ref 是当前 approved semantic artifact
→ authority_ref 必须 pin exact ApprovalRecord ArtifactRef
```

不要增加 `LATEST`、`PREFERRED`、`TEMPORARY` 等 speculative pointer kinds。

### 5.2 Mutable head 只是 locator

由于“谁是 current”本身必然可变化，需要一个最小 mutable head file。

head file 不是 semantic artifact，也不是历史事实；它只保存：

```text
current_pointer_ref: ArtifactRef
```

head 必须使用 strict canonical JSON，并由专门的 pointer store 管理。

历史 authority 来自 immutable CurrentPointer snapshots，不来自 head 文件过去的内容。

---

## 6. F4 — Pointer compare-and-swap

实现 lightweight file-backed CAS，不引入数据库。

建议 `FilePointerStore` / 等价类使用：

```text
compare_and_set(
  pointer_id,
  expected_pointer_ref | None,
  new target/authority
)
```

语义：

```text
expected = None
→ 只允许创建不存在的 pointer head

expected = exact CurrentPointer ArtifactRef
→ head 当前仍 exact-match 时才允许更新

mismatch
→ stale/conflict failure
```

### 6.1 Update 顺序

在 trusted local-filesystem boundary 下，建议：

```text
1. acquire exclusive per-pointer lock
2. read + verify current head
3. compare exact expected pointer ref
4. resolve/verify new target refs
5. write new immutable CurrentPointer artifact
6. write immutable SupersessionRecord（若非首次创建）
7. atomically replace tiny head file
8. fsync where practical
9. release lock
```

Lock 应使用最小 stdlib mechanism，例如 exclusive lock-file create；不要引入 service / DB。

如果 lock 已存在：fail explicitly；MVP 不自动偷取/推断 stale lock。

### 6.2 Crash semantics

如果在 head commit 前 crash，可能存在未被 head 引用的 immutable candidate pointer/supersession artifacts。

这类 artifact：

```text
historically stored
!= applied current transition
```

Active pointer history 必须从 current head 沿 `previous_pointer_ref` chain 解析；不得通过“扫描所有 CurrentPointer 文件然后猜最新”决定 authority。

禁止 timestamp-based latest selection。

---

## 7. F4 — SupersessionRecord

每次非首次 current transition 生成 immutable `SupersessionRecord`。

建议 payload 至少包含：

```text
SupersessionRecord {
  pointer_id
  pointer_kind
  superseded_pointer_ref: ArtifactRef
  superseding_pointer_ref: ArtifactRef
  superseded_target_ref: ArtifactRef
  superseding_target_ref: ArtifactRef
}
```

持久化建议：

```text
artifact_type = supersession_record
artifact_id   = pointer_id
revision      = superseding CurrentPointer revision
```

这样每次 transition 的 pointer snapshot 与 supersession record 可以 deterministic 对齐。

首次 pointer 建立无 supersession record。

SupersessionRecord 只记录 replacement fact，不删除/重写旧 artifact。

## 8. Current eligibility API

Foundation 至少提供等价能力：

```text
resolve_current(pointer_id)
is_current(pointer_id, artifact_ref)
require_current(pointer_id, artifact_ref)
```

`require_current()` mismatch 必须 fail closed。

Foundation 不实现 `REPLAY_COMPILE`；历史 replay caller 可显式 resolve historical ArtifactRef，而不调用 `require_current()`。

不得提供 generic `get_latest_revision()` 作为 current authority。

## 9. F5 — ValidationFinding

建议 immutable/lightweight model：

```text
ValidationFinding {
  finding_id
  code
  severity
  owner_stage
  repair_route
  message
  artifact_refs[]
  path?
}
```

要求：

1. `severity` 只能是 BLOCKING / REVIEW_REQUIRED / WARNING。
2. `owner_stage` 是 earliest authoritative owner stage identifier；Foundation 不枚举全部 A/B stages。
3. `repair_route` 是 machine-readable route identifier/text；不得只放 free-form human paragraph。
4. `artifact_refs` 使用 exact ArtifactRef，允许 finding 指向一个或多个 artifacts。
5. `finding_id` 必须 stable，后续 approval disposition 用它引用 exact finding。
6. Foundation 不写 stage-specific validation rules。

---

## 10. F5 — ValidationReport

建议 reusable model：

```text
ValidationReport {
  validated_refs: LineageRef[]
  findings: ValidationFinding[]
  summary {
    blocking_count
    review_required_count
    warning_count
    result
  }
}
```

### 10.1 Deterministic ordering

输入 findings 顺序不能影响 report canonical bytes/hash。

必须定义 deterministic sort key，例如按：

```text
severity rank
owner_stage
repair_route
code
finding_id
message
```

同理，`validated_refs` 也必须 deterministic order。

### 10.2 Summary/result 不信任外部输入

构造 report 时 summary/result 由 findings 派生。

从 persisted dict 恢复时，如果 serialized summary 与重新计算结果不一致：

```text
fail
```

不能“修正后继续”。

### 10.3 Structured schema adapter

可提供 generic helper 将 Draft 2020-12 validator errors 转成 `ValidationFinding`。

要求：

- path deterministic；
- code deterministic；
- caller 提供 owner_stage / repair_route；
- Foundation 不推断 business owner；
- schema validation 与 cross-artifact validation 最终都汇总为同一 ValidationReport。

### 10.4 Persistence

需要持久化时，ValidationReport 通过 Issue #1 `ImmutableArtifactEnvelope + FileArtifactStore` 保存。

不要创建第二套 JSON/hash/persistence implementation。

## 12. F6 — ApprovalRecord

建议 reusable model：

```text
ApprovalRecord {
  target_ref: ArtifactRef
  validation_report_ref: ArtifactRef
  decision
  reviewer_ref
  decision_timestamp
  review_item_dispositions[]
  reviewer_notes?
}
```

每个 disposition 至少：

```text
finding_id
value = ACCEPT_AS_DESIGNED | REVISION_REQUESTED
```

规则：

1. ApprovalRecord immutable，并通过 Issue #1 artifact substrate 持久化。
2. `target_ref` pin exact id/revision/content_hash。
3. `validation_report_ref` pin exact report。
4. reviewer identity 保持轻量，不引入 RBAC/PKI/signature infrastructure。
5. timestamp 是 explicit historical metadata；不得用 timestamp 推导 current approval。
6. reviewer notes 不成为 canonical business truth。

### 12.1 Generic APPROVE gate

Foundation-level approval verifier 对 `APPROVE` 至少 enforce：

```text
target_ref resolves exactly
validation_report_ref resolves exactly
report validated_refs covers/matches target according to caller-declared target role
report.result != FAIL
no BLOCKING
all REVIEW_REQUIRED findings have dispositions
all REVIEW_REQUIRED dispositions == ACCEPT_AS_DESIGNED
```

任意 REVIEW_REQUIRED = `REVISION_REQUESTED` 时不能 APPROVE。

Stage-specific prerequisites（例如 predecessor approval、bundle hash、release lineage）以后由 owning stage validator/gate 增加；Foundation 不编码 B1/B2/B6 business rule。

## 13. F6 — ApprovalRef

提供 reusable exact approval pin：

```text
ApprovalRef {
  target_ref: ArtifactRef
  approval_record_ref: ArtifactRef
}
```

resolver 必须验证：

```text
approval_record_ref resolves
record.decision == APPROVE
record.target_ref == target_ref
```

否则 fail closed。

ApprovalRef 不能只保存 `approval_record_id` 或 pathname。

## 14. Current approved pointer

复用同一个 `CurrentPointer` / pointer CAS infrastructure：

```text
pointer_kind = CURRENT_APPROVED

target_ref
= approved semantic artifact exact ref

authority_ref
= exact ApprovalRecord ArtifactRef
```

更新前必须验证：

```text
authority_ref resolves
ApprovalRecord.decision == APPROVE
ApprovalRecord.target_ref == target_ref
```

`REVISION_REQUESTED` 或 `ABANDON` 的 record 绝不能成为 CURRENT_APPROVED authority。

新 approved revision 成为 current-approved 时：

```text
旧 current approved pointer snapshot
→ 历史保留

旧 target/ApprovalRecord
→ 历史有效

新 CurrentPointer snapshot
→ current authority
```

不得先把旧 approved revision“失效”，再等待新 revision approval；replacement 成功后才移动 pointer。
