# B6.4 — Asset Binding / Resolution

状态：**FROZEN**

## 1. 职责

B6.4 从 B6.3 已评估的 candidate space 中，为每个 `AssetRequirement` 选择 concrete asset 或 compatible asset set，形成正式 binding proposal。

正式输出：

```text
EpisodeAssetBindingPlan
```

核心边界：

```text
AssetRequirement
≠ AssetCandidate
≠ ResolvedAssetBinding
```

B6.4 做 concrete selection，但仍不做 backend slot/order assignment。

## 2. 正式输入

只消费 exact：

```text
EpisodeAssetResolutionContext
EpisodeAssetRequirementPlan
EpisodeAssetCandidateEvaluationPlan
```

所有输入必须 pin id/revision/content_hash，禁止使用旧 evaluation 配新 requirement revision。

## 3. EpisodeAssetBindingPlan

至少包含：

```text
binding_plan_id
revision
content_hash
source_asset_context_ref
source_requirement_plan_ref
source_candidate_evaluation_plan_ref
resolved_asset_bindings[]
resolved_asset_sets[]
continuity_binding_groups[]
unresolved_requirements[]
binding_rationale_records[]
binding_summary
```

## 4. ResolvedAssetBinding

至少：

```text
binding_id
asset_requirement_id
resolution_status
selected_asset_refs[]
selected_asset_set_ref?
satisfied_capabilities[]
unmet_preferred_capabilities[]
continuity_group_refs[]
source_candidate_evaluation_refs[]
binding_rationale
review_flags[]
```

Resolution status：

```text
RESOLVED
RESOLVED_WITH_LIMITATIONS
UNRESOLVED
BLOCKED
```

`RESOLVED` 要求所有 required capabilities 满足。

## 5. Multiple assets

一个 requirement 可以绑定 1..N assets，只要 B6.2 `combination_policy` 允许。

正式引入：

```text
ResolvedAssetSet
```

它表示 semantic asset package，例如：

```text
Linsey visual set
= face_100 + full_body
```

必须保持：

```text
ResolvedAssetSet ≠ ProductionShotReferenceSet
```

B6 批准 semantic concrete asset universe；B7 决定每个 ProductionShot 实际用哪些 subset / role / order / slot。

## 6. Asset contribution / minimality

每个 selected asset 必须能说明 capability contribution。

遵循：

```text
minimum sufficient compatible asset set
```

禁止因“多给几张也许更好”造成 asset inflation。

但 semantic minimality 不等于 backend budgeting；B6 不因 H3 ref limit 删除 required assets。

## 7. Asset reuse

一个 `AssetRecord` 可以同时满足多个 requirements。

```text
one AssetRecord
→ many ResolvedAssetBindings
```

AssetRecord 不“属于”首先引用它的 requirement；binding 才描述使用关系。

## 8. Scope / inheritance

采用：

```text
most stable valid scope wins
```

例如 episode-level Linsey identity binding 应被多个 Shots reuse，而不是逐 Shot 重新选择 face。

可支持：

```text
SERIES / EPISODE
↓
SCENE / CONTINUITY GROUP
↓
PRODUCTION_UNIT
↓
PLANNED_SHOT
↓
UTTERANCE
```

但 inheritance 必须显式可解析，禁止 hidden default。

更低 scope 只有在存在明确 semantic requirement 时才可 refine/override broad binding。

## 9. Shot-specific refinement

例如 episode-level：

```text
Linsey visual = face + full-body
```

PS027 需要 profile support，则可增加 profile-compatible asset。

但不得无理由换成另一 incompatible identity/state family。

Override 应记录 reason，例如：

```text
ADDITIONAL_REQUIRED_CAPABILITY
CONTINUITY_STATE_CHANGE
SHOT_SPECIFIC_DETAIL
LOCALE_SPECIFIC_ASSET
```

## 10. Continuity-first binding

同一 `AssetContinuityGroup` 应整体选择 coherent asset family，而不是每 Shot greedy selection。

```text
local optimum ≠ continuity optimum
```

同一 canonical state可以使用 face/full-body/profile 等不同 files，但必须有 cross-asset evidence 证明 identity/appearance state一致。

建议记录 `ContinuityBindingGroup`，至少包含：

```text
semantic_subject_ref
canonical_state_ref
applicable_requirement_ids[]
applicable_shot_ids[]
selected_asset_refs[]
compatibility_evidence_refs[]
```

## 11. Selection priority

正式选择顺序：

1. satisfy all hard requirements
2. satisfy continuity constraints
3. preserve canonical/project asset preference
4. minimize asset count
5. maximize preferred capabilities
6. maximize reuse consistency
7. consider quality/aesthetic ranking

必须保持：

```text
semantic correctness first
```

## 12. Binding rationale

非 trivial binding应保存结构化 rationale，例如：

```text
selected_for_capabilities[]
rejected_alternative_refs[]
selection_factors[]
continuity implications
limitations
```

自由文本 explanation 可以由 Qwen产生，但不能成为唯一 authority。

## 13. Candidate eligibility

Final binding 只能选择：

```text
COMPATIBLE
COMPATIBLE_WITH_SUPPORT
```

或已经被 B6.3 验证为 compatible 的 `CandidateCombination`。

`PARTIALLY_COMPATIBLE` 只有在合法 evaluated combination 中 gap 被补齐时可作为成员。

`INCOMPATIBLE` / `INSUFFICIENT_EVIDENCE` 禁止直接绑定。

Human 有新信息时应先补 `HumanVerificationEvidence` → B6.3 reevaluation，而不是直接 override evaluation。

## 14. Project canonical assets

`PROJECT_CANONICAL` / human-verified asset 在同等 fitness 下应优先复用，尤其 character identity。

但 canonical label 不能覆盖 hard incompatibility。

Project canonical registry 与 episode binding 分离：

```text
Project Canonical Asset
= trusted/preferred identity source

Episode Binding
= this release variant actually uses
```

## 15. Release-specific assets

B5 产生的 localized screen text / language-specific voice requirement可以合法绑定 release-specific concrete assets。

例如：

```text
zh-CN phone text → phone_message_zh

en-US phone text → phone_message_en
```

只要语义与 approved ReleaseVariant一致。

## 16. Voice binding

通常：

```text
same speaker + same language/locale
→ same reusable voice identity binding
```

除非 canonical/release semantics 明确允许 voice-state change。

Utterance-specific `PREEXISTING_UTTERANCE_AUDIO` 可以显式覆盖 broader voice-reference binding，但二者仍是不同 asset kinds。

## 17. Unresolved requirements

B6.4 不强制伪造 resolution。

```text
REQUIRED + no compatible asset
→ UNRESOLVED
→ ASSET_CREATION_REQUIRED / CATALOG_EXPANSION_REQUIRED
```

Optional requirement 可 unresolved；是否可以继续由 B6.5 按 criticality 判断。

Placeholder asset 不得被标记 RESOLVED。

## 18. Upstream escalation

B6.4 不得修改 requirement 来迎合 available asset。

如果 requirement extraction错误 → B6.2。

如果 evidence/evaluation错误 → B6.3。

如果 missing concrete asset → creation/catalog expansion。

如果使用现有资产必须改变 B5/B4 semantics → route upstream。

正式原则：

```text
assets conform to approved semantics,
not semantics conform to available assets.
```

## 19. Effective binding index

可以 deterministic derive：

```text
EffectiveAssetBindingIndex
```

用于将 broad binding + specific refinement 展开到实际 consumer，例如 PlannedShot / utterance。

它是 derived index，不是 independent source of truth。

## 20. Backend firewall

B6.4 不决定：

- backend ref budget
- Picture N
- reference ordering
- H3/ComfyUI roles
- ProductionShot actual refs

## 21. 冻结原则

1. B6.4 从 evaluated candidate space 选择 concrete binding。
2. 输出 `EpisodeAssetBindingPlan`。
3. 一个 requirement 可绑定 1..N assets，受 combination policy约束。
4. 一个 AssetRecord 可服务多个 requirements。
5. ResolvedAssetSet 是 semantic package，不是 backend ref list。
6. 每个 asset 必须有 capability contribution。
7. 遵循 minimum sufficient set。
8. Continuity-first 优于逐 Shot greedy selection。
9. Same canonical state不要求 same exact file。
10. Scope inheritance显式可解析，无 hidden defaults。
11. Shot-specific override必须有 semantic reason。
12. Only evaluated-compatible candidates可 bind。
13. INSUFFICIENT_EVIDENCE不能直接绑定。
14. Human新 evidence先回 B6.3。
15. Semantic correctness优先于 aesthetics。
16. Project canonical是 preferred/trusted，不是强制万能解。
17. Voice identity与 utterance waveform分离。
18. REQUIRED missing asset保持 UNRESOLVED。
19. Asset substitution保持 B5 semantics时通常只需 B6 revision。
20. 需要改变 B5/B4 semantics 时必须 upstream escalation。
21. B6.4 不做 backend ref budgeting / slot assignment。
22. Binding revision immutable/versioned，refs exact pin。
