### Semantic-round decision gate

The frozen policy says one proposal plus at most one regeneration, and the CLI states a two-round maximum for a new window; neither explicitly grants a fresh budget after an unresolved claim. The implementation enforces two **per invocation**, because a window normally has one invocation and claims cannot be reclaimed. Thus the architecture does **not** establish that the ceiling resets per attempt. Treat the ceiling as applying across the entire window execution lineage unless an explicit architecture decision amends that policy. Unknown counts must be treated as potentially exhausted, not zero. For this incident the prior count is unknown, so **no new dispatch is permitted under the existing ceiling**. The proposed decision is one **additional** recovery invocation with a distinct cap of two semantic rounds and three technical attempts per round (at most six Provider attempts), under the normal rule that only a schema-valid semantic rejection triggers the second round. This is an exception to the conservative lineage-wide ceiling, not remaining original budget or a reset of the frozen policy. Its exact limits and authority require explicit architecture approval before implementation or authorization. Operator acknowledgment alone cannot grant that exception. This documentation PR approves neither the exception nor live execution.

Keep four quantities distinct: (1) original lineage usage is unknown; (2) the proposed new-attempt cap is separately authorized if the exception is approved; (3) actual new-attempt counts are recorded only when verified, otherwise null; and (4) the full lineage total remains unknown unless independently established from trustworthy complete evidence. Never add a known new count to an invented zero for the original. The record schemas below are conditional on that decision and do not authorize dispatch.

## State machine

All transitions that could authorize dispatch occur under the same story execution guard, with fresh authority and root checks. States are derived from verified immutable records, not an editable status flag.

```text
CLAIMED_UNRESOLVED + checkpoint absent
  -> ROOT_READY     (if needed, separately audited initialization; no dispatch authority)
  -> DECIDED        (durable, unique decision; policy gate satisfied)
  -> CONSUMED       (durable single-use attempt intent, before dispatch)
  -> CHECKPOINTED   (normal verified checkpoint; lineage link recorded)
  -> FAILED         (durable terminal result, checkpoint absent)
  -> OUTCOME_UNKNOWN (consumption exists, no trustworthy terminal result)

Any state + verified checkpoint -> VERIFIED_REUSE (takes precedence; zero dispatch)
  + no recovery evidence, or valid pre-consumption evidence only -> ORDINARY_AUDIT
  + durable consumption + complete matching lineage -> RECOVERY_AUDIT_COMPLETE
  + durable consumption + missing/incomplete lineage -> AUDIT_INCOMPLETE
  + malformed/conflicting/uncertain recovery evidence -> AUDIT_INCOMPLETE
No verified checkpoint + invalid/conflicting/ambiguous evidence -> BLOCKED (zero dispatch)
```

Audit classification is separate from semantic checkpoint verification and never permits regeneration of a verified checkpoint. A decision without consumption can be consumed once only after all checks are repeated and checkpoint absence is confirmed; a verified checkpoint prevents its consumption. Once consumed, it can never authorize another invocation, including after a crash before the first network call. `FAILED` and `OUTCOME_UNKNOWN` both prohibit additional recovery by default. A failure to persist a terminal record leaves `OUTCOME_UNKNOWN`; absence of a terminal record never proves no dispatch. No timeout, stale lock, restart, or operator identity creates a new authorization. A new architecture decision and separately reviewed protocol would be needed for any further attempt; this v1 provides no override.

## Proposed v1 records

Use strict canonical JSON, bounded sizes, closed field sets, SHA-256 `content_hash` of the canonical object excluding its own identity, and exact round-trip verification. Reject unknown versions, duplicate keys, noncanonical bytes, bad hashes, symlinks, unsafe files and inconsistent references. Names are deterministic from the original claim identity and record type in the **existing execution root**; at most one decision, one consumption and one terminal record per claim. A no-clobber fixed slot prevents competing decision IDs from creating parallel authorizations. Record IDs are content identities; timestamps are UTC audit metadata, never expiry or proof of ordering. No source text, responses, credentials or exception messages belong in these records.

* **Root initialization intent/result v1**: separate immutable fixed-slot canonical records in the execution root, each with version, type and content identity. The intent binds operator, time, reason, original claim identity and exact-byte hash, preparation/window/request, trusted canonical checkpoint parent path and inode, desired final path, and the observed historical fact that the root was absent at incident inspection. The result binds the intent, initialization-time absence observation, newly created root path and `(st_dev, st_ino, file type)`, verified ownership/mode, parent identity and successful parent sync. Neither record is a decision or dispatch authorization. A pre-existing verified recovery-time root needs no initialization record; its current identity is still bound by the decision.
* **Decision v1**: `schema_version`, `record_type`, `decision_identity`; unique `decision_id`; `operator_id`, `decided_at`, bounded `reason`, evidence references/digests (including forensics and any independently verified observations), explicit `prior_outcome: unknown`, `ack_prior_requests_may_have_completed: true`, `ack_duplicate_generation_possible: true`; `claim_identity` and SHA-256 of the exact canonical claim bytes; `preparation_identity`, window ID/ordinal, `request_identity` and semantic request hash; full source snapshot and hash identifying A5/A6 refs/revisions/hashes and CURRENT authority, B1.2 strategy ref/hash and selection mode plus CURRENT pointer ref if applicable; canonical execution, checkpoint, artifact and pointer root paths and device/inode identities; root-initialization result identity when applicable; policy-decision reference and approved new-attempt caps; exactly one `attempt_id`. Values must match a freshly rebuilt trusted session and original claim; a signed policy decision is not inferred from the operator's data.
* **Consumption/attempt intent v1**: `schema_version`, `record_type`, `consumption_identity`, decision identity and ID, claim identity and claim-byte hash, same attempt ID, `consumed_at`, and digest of the exact revalidated authority/root/session bindings and budget. Its durable publication is the irreversible single-use point, before any Provider dispatch. It says **may have dispatched**, never that dispatch occurred.
* **Terminal v1**: `schema_version`, `record_type`, `terminal_identity`, decision and consumption identities, attempt ID, `recorded_at`, outcome `CHECKPOINTED` or `FAILED`, bounded safe failure code or null, verified actual new-attempt counts or null, original usage and full lineage total as unknown unless independently established, and for `CHECKPOINTED` the exact checkpoint identity and SHA-256 of canonical checkpoint bytes. Unknown counts remain null, not zero. `FAILED` is permitted only after a fresh verified checkpoint-absence check; if anything is uncertain, omit terminal and leave outcome unknown. A valid checkpoint found later wins over an earlier failure record, which remains immutable as historical evidence.

The exact root identity is the canonical path and `(st_dev, st_ino, file type)` of each opened root, validated against the trusted parents and disjoint protected trees. Capture and compare all four roots at decision and consumption; after the initialization procedure below, an absent or replaced root fails closed. A newly initialized checkpoint root inode is recovery-time evidence only; never assert that inode existed during the original dispatch. Keep the same root instances while guarded. Artifact refs, source snapshot, strategy selection and request must be checked structurally and through existing authority verification, not only by comparing hashes. Record the relevant A5/A6 CURRENT references and B1.2 CURRENT selection when applicable; re-resolve them before dispatch and checkpoint. Runtime/tokenizer freshness and budgets must be re-established as for the normal runner; runtime-only settings remain distinct from semantic identity.

## Atomic persistence and crash consistency

Reuse the existing private root, directory-descriptor/no-follow, stable-file and inode checks, bounded strict reads, exclusive flock and same-directory temporary-file, file-fsync, no-clobber hard-link and directory-fsync pattern used by claims/checkpoints. Add a narrowly scoped record codec/store; do not rename, rewrite, delete, or reset the original claim or checkpoint. Create recovery records in the execution root and, only under the initialization procedure below, the absent checkpoint root's final directory component. Before success, check ownership/mode, root identity and exact canonical bytes.

Write and fsync the complete private temporary file, link it to its fixed final name without replacement, then fsync the directory and verify the exact final record. Dispatch is forbidden unless **both** decision and consumption have completed these steps successfully in the current guarded operation. Existing identical decision evidence may be read for inspection; it never overrides a consumption. Conflicting, malformed or partial fixed-slot evidence blocks. Any write, link, verification or fsync failure stops without dispatch; if a link may have succeeded, its existence or durability is uncertain and must not be treated as absent. Crash leftovers and uncertain durability require read-only investigation, not automatic cleanup or reauthorization. A durable consumption discovered on restart is spent regardless of whether dispatch occurred; if its durability is uncertain, block as well. Temporary files are never authority; suspicious remnants or inability to establish a clean state block, and their disposition requires separate review. Do not rely on atomicity across files: decision precedes consumption; consumption precedes dispatch; checkpoint precedes terminal. Each stage must stand safely alone.

On success use the existing `save_checkpoint` and verify its exact bytes by normal loading while holding the guard, then publish the terminal link. If checkpoint publication or directory fsync has an uncertain outcome, stop and inspect on a later invocation; verified checkpoint takes precedence. A terminal write failure cannot invalidate a checkpoint or authorize another attempt. The sidecar can be completed only from verified, uniquely bound evidence under guard, without Provider calls; otherwise flag an audit gap. No deletion of evidence to resolve a conflict.

## Initially absent checkpoint root

The historical observation that Alice's checkpoint root was absent during incident inspection is distinct from its state at recovery time. The original execution root and claim remain untouched. The following is a proposed initialization protocol for a future implementation, not authorization to run it in this PR:

1. Under the existing exclusive execution guard, verify the exact canonical original claim bytes and identity, rebuild and verify authority and request, and inspect the expected checkpoint without creating anything. A verified checkpoint takes precedence; invalid or uncertain evidence blocks. Verify the configured absolute checkpoint path, its existing canonical, trusted, operator-owned parent (not group/world writable), non-symlink components and disjointness from execution and protected roots. Inspect the fixed initialization slots before classifying the root: an incomplete, invalid or conflicting intent/result blocks even if the directory now exists. Confirm the final component is absent with safe no-follow inspection; if it is already present with no initialization evidence, validate it as an existing root and do not claim to have initialized it. If a complete result exists, verify its bound inode and retain its link in subsequent evidence.
2. Durably publish the initialization intent in the existing execution root using the same no-clobber, file-fsync and directory-fsync record protocol. Revalidate guard, claim, checkpoint absence, parent identity, root separation and final-component absence. Create only the final component with private `0700` permissions, compatible with checkpoint storage's final-component `mkdir` and parent-directory fsync pattern. An unexpected `EEXIST`, symlink, replacement or ambiguity blocks rather than adopting a concurrent creation.
3. Open the new directory without following symlinks, verify its type, owner and private mode and stable path/descriptor `(st_dev, st_ino, file type)`, fsync the trusted parent directory and revalidate the parent and root identity. Reverify the original claim bytes and expected checkpoint absence, authority and guard. Durably publish and verify the initialization result in the execution root binding the new inode and intent. Later decision and consumption records must bind that exact result and inode; revalidate both immediately before any dispatch.

Initialization is a separate audit event and **never authorizes generation**. On any failure, crash, uncertain mkdir or fsync, missing/conflicting intent or result, changed identity or concurrent modification, stop and block; a possibly created root is not automatically adopted, removed or recreated. Investigation and any resolution require a separately reviewed procedure. Do not invent a historical inode or modify the claim, checkpoint or CURRENT. The existing checkpoint storage primitive alone does not implement this audit protocol.

## Operator authorization sequence

1. Obtain an explicit architecture decision approving the proposed separately bounded exception to the lineage-wide round ceiling. Without it, stop. Review forensics and exact claim bytes, checkpoint absence, trusted roots and authority; do not interpret server task matches as accepted responses or known counts.
2. Identify the operator, reason and evidence; explicitly acknowledge both possible prior completion and duplicate generation. Display the exact window, claim-byte hash, request, authority, roots, approved budget and policy reference. This is a proposed retry decision only, not semantic or publication approval.
3. Acquire the **existing** exclusive execution guard and hold it through any needed audited checkpoint-root initialization, decision, consumption, execution and checkpoint/terminal persistence. If the checkpoint root is absent, complete the initialization protocol first; it grants no dispatch authority. Freshly rebuild the complete preparation and request, revalidate A5/A6 CURRENT, B1.2 selection, all root identities and disjointness, pinned prompt/profile/schema, runtime, tokenizer and budgets. Verify exact original canonical claim bytes. Run normal resume verification: a verified checkpoint immediately yields reuse; invalid checkpoint or claim blocks. Inspect all fixed recovery slots; conflict, consumption, terminal, unknown evidence or changed bindings blocks.
4. Publish and durably verify the one decision. Repeat guard/root, claim, checkpoint, authority, request, budget and recovery-slot checks immediately before consuming. If any changed, stop; no decision can be repurposed for another identity. Publish and durably verify the single consumption. Recheck guard, authority and checkpoint before dispatch; failure after consumption spends the attempt and stops.
5. Only if the separate policy decision permits it, invoke one bounded attempt with normal runtime, provenance, schema and semantic checks and technical limits. Revalidate authority after responses and before acceptance; hold guard through the normal checkpoint save and verification. No regular runner path may invoke this exception. A normal runner still rejects every unresolved or invalid claim for every missing window, even if a decision exists.
6. Write the terminal record after verified checkpoint or safely observed failure; if terminal persistence fails, report unknown and stop. On later inspection check checkpoint first. Additional recovery is prohibited by v1. Independently perform reconciliation, whole-plan validation, human review and publication approval under their existing contracts; none follows from retry authorization or local semantic acceptance.

## Checkpoint and proposal provenance

The v1 checkpoint filename and identity remain derived by the existing codec from the same preparation/window/request and accepted payload; a recovery ID is **not** substituted into either. As the preferred compatibility option, subject to a separately reviewed architecture decision, retain the existing v1 encoding and identity. Its counters describe the completed invocation represented by that checkpoint; they do not describe the unknown prior execution or full lineage. This clarification must be reconciled with existing code comments describing window totals before implementation. The accepted proposal retains the actual recovered invocation's provenance and internally consistent round/rejected-round/provider-attempt evidence. Never fabricate original counts or mark them zero. If the invocation cannot provide verified accounting, do not manufacture a valid checkpoint.

For a checkpoint associated with durable recovery consumption, before B1.3 reconciliation or any other downstream stage treats it as authoritative input, including acceptance and publication, the downstream audit gate must independently verify a complete recovery sidecar lineage: exact original canonical claim bytes and identity -> approved decision and its authority, root and budget bindings -> durable consumption -> unique attempt -> terminal link -> exact checkpoint identity and canonical-byte hash. Verify every record's canonical bytes, identity and cross-references, the matching invocation provenance and verified new-attempt accounting, and any required root-initialization record. Preserve original usage and full lineage total as unknown unless independently established. This is an additional audit gate, not a change to the ordinary checkpoint verifier's semantic validity.

Downstream audit inspects the exact claim and all applicable fixed recovery slots under the trusted roots. Claim presence alone is not evidence of recovery: the normal runner creates a claim before generation and retains it after a successful checkpoint. A normally verified checkpoint with a claim and no recovery evidence is ordinary verified reuse and needs no recovery sidecar. Valid root-initialization evidence or a valid decision with **no consumption**, and no conflicting or uncertain evidence, likewise records only pre-dispatch recovery activity: report it, do not invent a Provider attempt, and treat the verified checkpoint as ordinary for this recovery audit. The checkpoint prevents that decision from being consumed.

Durable consumption is the irreversible authorization boundary; it means the attempt **may** have dispatched, not that it did. A verified checkpoint associated with consumption requires complete matching recovery lineage for downstream audit acceptance. Missing required lineage after consumption, or malformed, conflicting, mismatched or uncertain recovery evidence, including uncertain consumption or incomplete initialization or decision writes, yields `AUDIT_INCOMPLETE`; never infer clean absence from an unreadable or uncertain slot. Preserve the evidence and block B1.3 reconciliation and every other downstream use as authoritative input until the audit is complete. A verified checkpoint remains semantically valid under the ordinary verifier and always prohibits additional generation, regardless of audit status. A sidecar may be completed only from uniquely verified existing evidence under guard, without Provider calls; otherwise remain `AUDIT_INCOMPLETE`. Existing readers do not enforce this gate, so a future implementation must explicitly implement and test it before downstream use. Do not alter the ordinary checkpoint codec or claim semantics. Retry authorization is separate from semantic validity, reconciliation, human review and publication approval.

## Failure-mode matrix

| Condition | Required result |
| --- | --- |
| Verified checkpoint before decision, consumption, or dispatch; including after uncertain save | Reuse verified checkpoint; no dispatch; retain all records. |
| Malformed, conflicting or noncanonical claim/checkpoint/record; root or authority mismatch | Block; no dispatch; preserve evidence. |
| Checkpoint-root initialization mkdir, verification or parent fsync fails or crashes | Block; preserve any root and records; no automatic adoption, cleanup or dispatch. |
| Verified ordinary checkpoint + retained claim, no recovery evidence | Ordinary verified reuse; no sidecar required; no generation. |
| Verified checkpoint + valid initialization and/or decision, no consumption or uncertainty | Ordinary recovery-audit classification; report pre-dispatch records without inventing an attempt; no consumption or generation. |
| Verified checkpoint + durable consumption and complete matching lineage | Recovery audit complete; no generation; other semantic and approval gates still apply. |
| Verified checkpoint + durable consumption and missing/incomplete lineage, or malformed/conflicting/uncertain recovery evidence | `AUDIT_INCOMPLETE`; no generation; block reconciliation and all downstream authoritative use pending audit completion. |
| Decision write/link/fsync fails or crashes | No dispatch; uncertain final slot blocks automatic continuation. |
| Consumption write/link/fsync fails or crashes | No dispatch in that process; present or uncertain consumption is spent/blocked, never retried. |
| Crash after consumption, before/during/after Provider call | Outcome unknown, even if no call actually happened; no further dispatch. |
| Provider/parse/provenance/semantic/authority failure after consumption | Stop; record safe failure only if checkpoint absence and evidence are verifiable; otherwise unknown. Counts may be null. |
| Accepted response but checkpoint save/link/fsync fails | Stop; inspect exact checkpoint later; verified checkpoint wins, absent/uncertain remains spent and unknown or safely recorded failure. |
| Checkpoint durable but terminal write fails | Reuse checkpoint without generation; `AUDIT_INCOMPLETE` blocks downstream authoritative use; reconstruct only if unique verified evidence permits. |
| Two operators or a normal runner race | One guard serializes cooperating processes; fixed no-clobber slots reject competing decisions; later process rechecks checkpoint and consumption. |
| A5/A6/B1.2 authority or root changes at any revalidation | Block; if consumed, attempt remains spent; never move records to a new identity. |

## Threat and concurrency boundary

The protocol assumes trusted operator-owned stable parents, private roots, reliable local flock/hard links/fsync and cooperating executors using the same roots. The advisory lock cannot constrain non-cooperating processes, other roots, privileged modification, hostile mounts or a lying filesystem; these are outside the existing primitive's guarantee and require operational controls. Hashes detect mismatched bytes, not malicious edits by a root owner; operator identity is an audit assertion unless a separately specified authentication system verifies it. Guard and no-clobber slots prevent two cooperating operators from consuming once each, not duplicate requests already sent by the Provider or technical retries inside the one permitted attempt. Authority may change in another subsystem despite the lock; existing before/after authority checks prevent acceptance on observed change, not Provider-side cancellation. A verified checkpoint is authoritative only after the existing session and authority verification succeeds; invalid evidence is never treated as absence.
