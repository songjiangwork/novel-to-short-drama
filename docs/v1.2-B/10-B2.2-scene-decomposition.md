# B2.2 — Scene Decomposition

状态：**FROZEN**

## 1. 职责

B2.2 将 `EpisodeScreenplayContext` 分解为有序 `EpisodeScenePlan`。

回答：

```text
本集 approved presentation material 应拆成哪些 ScreenplayScene，
这些 Scene 以什么顺序出现，
每个 Scene 完成什么 dramatic function？
```

不负责最终 dialogue/action，也不处理 camera / shot / asset / H3 / ComfyUI。

## 2. EpisodeScenePlan

正式输出：

```text
EpisodeScenePlan
├── upstream pins
├── ordered ScreenplayScenes
├── PresentationSceneMappings
├── BeatSceneMappings
├── SceneContinuityContracts
├── scene duration budgets
└── coverage summary
```

`EpisodeScenePlan` 是 screenplay-level creative planning artifact，不是 adaptation truth。

它拥有独立 revision/hash；B2.3 必须 pin exact revision。

## 3. ScreenplayScene

`ScreenplayScene` 是 screenplay presentation order 中局部连续、具有明确 dramatic function 的单元。

至少包含：

```text
scene_id
scene_order
dramatic_setting
scene heading semantics
participants
scene_objective
conflict
turn
outcome
presentation coverage
beat coverage
opening continuity requirements
ending continuity commitments
duration budget
```

Scene 是 dramatic unit，不是 Shot container。

## 4. Split / merge 规则

`1 AdaptedBeat → many Scenes` 合法。

强 split signals 包括：

- meaningful location change
- significant time discontinuity
- major participant constellation change
- new scene objective
- new dramatic conflict
- meaningful temporal ellipsis
- reveal / withholding boundary
- major emotional/power reset
- distinct presentation treatment

不能因为动作多、对白多、人物多或需要多个 Shot 就拆 Scene。

`many adjacent AdaptedBeats → 1 Scene` 合法，前提是 presentation 顺序、setting/time、participants、causality、reveal/withholding 与 dramatic arc 均兼容，且每个 Beat 的 required effect 仍可识别。

禁止 merge 导致 reveal 提前、withholding 被破坏、因果顺序混乱、knowledge 提前、setup/payoff 被压扁或跨越 B1 presentation boundary。

## 5. PresentationSceneMapping

除 B2.1 已冻结的 `BeatSceneMapping` 外，B2.2 正式增加：

```text
PresentationSceneMapping
```

原因：

```text
AdaptedStoryBeat = what happened
PresentationEntry = when/how audience encounters it
ScreenplayScene = how that presentation is dramatized
```

`PresentationEntry ↔ ScreenplayScene` 支持 many-to-many。

## 6. Scene order

B2.2 不拥有重新决定 presentation order 的 authority。

Scene ordering 必须对 Primary Presentation Sequence 保持 monotonic consistency。

B2.2 可以 expand presentation order，但不能 rewrite presentation order。

多个 PresentationEntries 合并到同一 Scene 时，Scene 内部 presentation order 仍必须明确。

## 7. Scene identity

`scene_id` 具有 stable semantic identity。

只改 dialogue wording、action wording、minor pacing、reaction、subtext 等 realization 内容时保持 scene_id。

若发生 scene split/merge、major beat/presentation reassignment、dramatic setting 或 scene objective 的根本变化，应产生新的 Scene identity，并可保留 lineage（derived_from / replaces / supersedes）。

## 8. DramaticSetting / SceneHeading

`DramaticSetting` 与 `SceneHeading` 分离。

```text
DramaticSetting
= stable semantic place identity

SceneHeading
= INT/EXT + dramatic_setting_id + time descriptor + optional qualifier
```

DramaticSetting 应有 stable ID，支持跨 Scene 重用；它不是 ProductionLocation 或 asset。

## 9. Participants

Scene participants 指 dramatically relevant `AdaptedCharacter`。

背景 crowd 不要求创建大量 AdaptedCharacter。B2.2 不得偷偷创建新的 narrative character。

## 10. SceneContinuityContract

B2.2 正式引入：

```text
SceneContinuityContract
```

表达：

```text
required opening conditions
+
required ending commitments
```

采用 sparse representation，只记录本场依赖或改变的 narrative-relevant state。

它是 planned contract，不是 realized state。

## 11. Coverage

B2.2 必须证明：

```text
Presentation Coverage
Beat Coverage
```

每个本集 required PresentationEntry 至少被一个 Scene 覆盖。

每个 required AdaptedStoryBeat 的必要 dramatic function 必须被 Scene 覆盖；BeatSceneMapping 应说明 Scene 实现 Beat 的哪一部分 function。

## 12. Duration budget

每个 Scene 拥有 screenplay-level duration target/range。

```text
Scene duration budget ≠ final edit duration ≠ shot duration
```

它用于控制 B2.3 realization 的 pacing feasibility，而不是规定镜头数量或实际视频 timing。

## 13. 与 B2.3 / Production 的边界

B2.2 决定：

```text
这场戏为什么存在
在哪里
什么时候
谁参与
objective / conflict / turn / outcome
覆盖哪些 presentation / beats
大约多长
```

B2.3 决定人物具体做什么、说什么、如何反应与停顿。

Production / Shot Planning 决定 camera、lens、framing、movement、coverage、reference asset 等。

## 14. Route upstream

若发现上游无法合理戏剧化，B2.2 不得 silent repair。

按 earliest authoritative owner route：

```text
presentation design → B1.4
episode membership / boundary → B1.5
AdaptedBeat semantics → B1.4
source disposition → B1.3
global strategy → B1.2
```

## 15. 冻结 contract

1. B2.2 输出 ordered EpisodeScenePlan。
2. ScreenplayScene 是 stable-identity dramatic unit，不是 Shot container。
3. Beat ↔ Scene、PresentationEntry ↔ Scene 均支持 many-to-many。
4. 正式存在 BeatSceneMapping 与 PresentationSceneMapping。
5. B2.2 不得重排 Primary Presentation Sequence。
6. 每个 Scene 至少表达 objective / conflict / turn / outcome。
7. DramaticSetting 与 SceneHeading 分离；DramaticSetting 有 stable identity。
8. SceneContinuityContract 使用 opening requirements + ending commitments。
9. 必须验证 Presentation Coverage + Beat Coverage。
10. 每个 Scene 分配 screenplay-level duration budget。
11. EpisodeScenePlan 拥有 revision/hash；B2.3 必须 pin exact revision。
12. Structural split/merge 产生新 Scene identity；realization-only revision 可保留 Scene ID。
13. B2.2 不增加 formal human approval gate。
14. Qwen 负责 semantic decomposition，Python 负责 IDs/order/reference/coverage/validation。
15. B2.2 不得创建 AdaptedStoryBeat 或改变 adaptation/presentation truth。
