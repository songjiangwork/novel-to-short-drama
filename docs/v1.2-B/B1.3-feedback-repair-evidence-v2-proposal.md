# B1.3 feedback repair and checkpoint evidence v2

Status: **PROPOSED / NOT RATIFIED**. Refs #121.

This document proposes a contract for independent architecture review. It is not an approval, an implementation, an authorization to call a Provider, or an instruction to alter an unresolved claim. The older `window_0001` R0D proposal is incident-specific and is not approval for this proposal or for `window_0004`.

## Scope and evidence

Three Alice windows have verified v1 checkpoints; `window_0004` has an unresolved claim and no checkpoint. In one isolated experiment, the original v3 request produced a schema-valid candidate with active event mapping coverage of 3/9 non-omit owned events. A separate request to the same model, supplied that candidate and precise validator feedback, produced 9/9 coverage and passed the production semantic validator. This is one observation, not a guarantee of future generation or a narrative-quality approval. Alice acceptance remains 3/14.

The proposal changes only feedback and its auditable execution evidence. It does not alter the frozen [source disposition and mapping invariants](03-B1.3-source-story-disposition.md), validator acceptance rules, Prompt v3, output schema, or semantic profile. Python must not invent model-authored retained/transformed semantics or provenance. It does not define claim recovery, new authorization, a third round, an automatic retry mechanism, or publication of Alice output.

## Round and identity contract

1. Round 1 uses the existing exact packet, Prompt v3, schema, semantic profile, base semantic request identity and normal request/provenance checks. Its model, Provider family, authority, output reservation and attempt accounting remain bound as today. A successful first round uses the existing v1 checkpoint path and codec.
2. At most two semantic rounds remain permitted. Feedback is enabled only after schema validation and the exact static semantic rejection `kept/compressed/merged owned event requires an active mapping candidate`. All other semantic rejections **fail closed** in feedback mode; schema, transport, provenance and authority failures do not trigger feedback. No exception text is inserted into a prompt or emitted to logs.
3. The retained first candidate is the complete schema-valid **parsed JSON**, encoded with the project's canonical JSON encoding; it is not the raw HTTP envelope, response bytes, headers, or a provider transcript. The feedback renderer is a separately versioned, pinned asset with an exact content hash. It takes the trusted packet, this candidate, and a fixed versioned diagnostic rule. The renderer gives the model the complete candidate and the exact missing owned event references, original dispositions and related beats/mappings. It asks for a complete corrected proposal, with semantically supported mappings; it must not ask the model to fabricate events, arbitrarily mark events omit, or invent unsupported mappings merely to pass.
4. The diagnostic independently scans owned refs in trusted packet order, considers only non-omit dispositions and event mappings, and emits all missing events in 1-based order, classified as `NO_EVENT_MAPPING` or `ONLY_INACTIVE_EVENT_MAPPINGS`. It uses the existing static rule code, never arbitrary exception text. Unknown, inconsistent, duplicate or oversized input, unsupported rule/version, or incomplete/truncated diagnostics stop the invocation; never send a partial correction. This extraction does not change validator behavior.
5. Round 2 has its own pinned feedback-prompt identity, rendered prompt hash, structured request hash and actual invocation provenance. These bind the exact candidate and deterministic feedback in the rendered request. Round 2 keeps the original schema, semantic profile and declared model/Provider family. The base request identity remains the stable preparation/window and claim binding; it must never be presented as the round-2 request hash. Technical attempts remain at most three per round and at most six per invocation under the existing policy.

## Proposed v2 evidence and verification

Use a closed, canonical, version-tagged v2 checkpoint for a successful **different-request feedback round only**. Proposed required evidence is grouped below; exact field names and encoding require approval before implementation:

| Group | Required bindings |
| --- | --- |
| Envelope | Codec/schema version, artifact type, checkpoint identity over every other field; bounded canonical bytes with duplicate and unknown fields rejected. |
| Authority | Preparation identity, source snapshot hash, exact B1.2 strategy ref/hash, window ID/ordinal/packet hash, base request identity and round-1 semantic request identity. |
| Round 1 | Prompt/profile/schema identities, rendered and structured request hashes, actual invocation provenance and provider-attempt count; canonical parsed candidate and its hash; fixed rejection rule/version and complete deterministic diagnostics. |
| Round 2 | Feedback template ID/version/content hash, diagnostic version, independently rebuilt rendered prompt hash and request hash, actual invocation provenance and provider-attempt count. |
| Accepted result | Final proposal, semantic rounds = 2, total attempts and per-round accounting, plus enough versioned asset identifiers to reconstruct both requests. |

Verification must rebuild authority, packet and frozen round-1 assets from the trusted session; check the base identity and round-1 provenance; verify canonical candidate bytes/hash and schema; rerun the unchanged semantic validator and require the exact supported rejection; recompute and compare the complete diagnostics and deterministic feedback; rebuild the pinned round-2 request and compare both hashes and its actual provenance; then schema- and semantic-validate the final proposal against the same packet. Check all accounting and the v2 checkpoint identity. Never substitute the base identity for round-2 provenance or accept merely because stored hashes agree with one another.

The current provenance records declared routing and request metadata, not a cryptographic attestation of the actual model or of response contents. Even retaining the first candidate proves only internal consistency under the trusted execution/storage boundary; it does not independently prove which model produced the response. Unknown version, asset, candidate, diagnostic, request identity, provenance or validation mismatch must reject the whole checkpoint.

## Storage, resume and publication compatibility

Keep every v1 file, path, codec, identity and byte unchanged; no migration. Continue to read existing v1 checkpoints using their original rules. A first-round success remains v1. A feedback success uses a distinct v2 filename/codec whose locator is bound to the same preparation, window and **base** request identity; the round-2 hash is evidence inside it, not a new way to evade the existing claim. The final filename syntax is subject to review.

| Observed state for a preparation/window | Required result |
| --- | --- |
| Exactly one valid v1 for the expected base request; no competing checkpoint | Verify and reuse v1 unchanged. |
| Exactly one valid v2 for the expected base request; no competing checkpoint | Verify both rounds and final proposal, then reuse v2. |
| Both v1 and v2, multiple versions, or different request identity for that window | Conflict: fail closed; do not select, overwrite or generate. |
| Unknown version, malformed name/evidence, damaged file, unverifiable asset or identity mismatch | Fail closed; do not treat as absent or regenerate. |
| No checkpoint and unresolved/invalid claim | Block generation under the existing claim rule. |

The loader must inspect all recognized version namespaces for the same preparation/window, not merely today's `b13-checkpoint-v1` prefix. It must also fail closed on an unknown checkpoint version attributable to that window. A rollout must prevent older writers, which cannot see the v2 namespace, from dispatching against a v2-capable root. Root isolation, no-clobber writes and cross-request conflict checks remain mandatory.

Resume verifies v1 or v2 using the matching codec and exposes the same validated accepted proposal to B1.3-B3 reconciliation, with base and per-round identities kept distinguishable. Reconciliation still performs its existing review; neither semantic PASS nor checkpoint reuse is narrative approval.

B4A currently reconstructs a single request for all rounds. A versioned B4A publication evidence contract must instead carry or securely reference the complete v2 evidence needed to independently rebuild both rounds, and bind it to the final proposal and publication identity. A self-contained publication carrying the rejected candidate is permissible only in a storage domain approved for the same private access and retention controls as v2; if the destination cannot enforce those controls, publication fails closed. Existing v1 publication verification remains unchanged. No v2 result is eligible for authoritative publication until this verification path exists and passes; a checkpoint-only upgrade is insufficient.

## Budget, privacy and failure boundaries

- Before round 1, retain the current full preparation, authority and budget checks. The feedback input is not known yet: after round-1 rejection and before round-2 dispatch, build the actual round-2 request and check its actual mapped-body estimator, trusted server tokenizer, input ceiling, verified context capacity and unchanged output reservation. Unknown, failed or excessive measurements stop without a second dispatch; no truncation or guessed budget is allowed. Revalidate authority and runtime according to the existing boundary.
- Proposed maximum for the canonical first candidate is **262,144 bytes**; proposed maximum for the entire canonical v2 checkpoint is **1,000,000 bytes**. Oversize candidate, feedback or resulting evidence fails closed; never truncate. The whole-checkpoint limit includes both candidates and all metadata and is checked before publishing. These limits require explicit approval and may reject otherwise schema-valid output.
- Until acceptance, retain the candidate and feedback only in protected process memory. On a successful feedback round, the first parsed candidate is retained solely inside the private v2 evidence and, if approved, its equivalently protected publication evidence. On failure, do not persist the rejected candidate or raw Provider response; leave the unresolved claim and return only bounded safe diagnostics. Never log candidate text, source text, prompt, raw response, local keys, source IDs or arbitrary exception messages. The corrected proposal remains subject to existing downstream review.
- V2 files require a trusted operator-owned private root, private `0600` files and a `0700` root; preserve existing symlink, no-clobber, fsync, atomic publication and exact read-back checks. Retention is tied to the checkpoint/publication evidence lifecycle; no separate debug copy or unbounded retention is introduced. Retention duration and access authorization require human approval before deployment.
- Hold and verify the original execution guard throughout claim creation, both rounds, durable checkpoint write and verification. Never remove, reset, replace or bypass an unresolved claim; uncertain dispatch, budget failure, semantic exhaustion, write/fsync failure or verification failure stops the invocation and preserves evidence. No automatic retry or new execution root is authorized by this proposal.

## Focused regression and implementation boundaries

At minimum, offline synthetic tests must cover: v1 bytes/identity and reuse unchanged; first-round success still v1; exact supported rejection and deterministic feedback; two distinct request hashes/provenances and attempt accounting; rejected candidate, diagnostic, prompt, final proposal or identity tampering; malformed/unknown/oversized evidence; input/tokenizer/output-reservation failure before round 2; no third round; v1/v2 and cross-request conflicts; guard, claim, write/fsync and read-back failures; and v2 checkpoint → resume → reconciliation → versioned B4A independent verification. Include tests that logs and failure summaries do not expose candidate or source contents.

After independent approval, at most two small implementation Draft PRs are proposed:

1. **Offline evidence and compatibility:** versioned feedback asset/diagnostic and v2 codec, deterministic two-request reconstruction, v1 preservation and all-version conflict tests. No live dispatch.
2. **Execution and downstream verification:** guarded feedback dispatch with actual round-2 budgets, v2 durable save/resume and versioned B4A compatibility, plus focused end-to-end synthetic regressions. No automatic claim recovery.

## Open human decisions

Architecture approval must explicitly decide: retention of a schema-valid rejected candidate and the proposed size/access/retention limits; the precise feedback template and diagnostic contract; two-request identity and v2 checkpoint/publication wire formats; mixed-version conflict and rollout rules; runtime tokenizer trust and failure behavior; and authorization for any separate future live incident. Approval of this document or merging a PR alone must not be represented as incident-specific live authorization.
