# B6.3 — Asset Candidate Discovery + Compatibility Evaluation

状态：**FROZEN**

## 1. 职责

B6.3 针对 B6.2 已冻结的 `AssetRequirement`，从 B6.1 已 pin 的 asset universe 中发现 concrete candidates，并基于可验证 evidence 判断它们对 requirement 的适配程度。

正式输出：

```text
EpisodeAssetCandidateEvaluationPlan
```

核心边界：

```text
AssetCandidate ≠ ResolvedAssetBinding
```

B6.3 说明“哪些可以用、为什么”，不做最终 selection。

## 2. 正式输入

消费 exact：

```text
EpisodeAssetResolutionContext
EpisodeAssetRequirementPlan
pinned AssetCatalogs
AssetAvailabilitySnapshot
```

所有 formal candidate 必须属于 B6.1 已 pin 的 catalog universe。

禁止 silent 目录扫描、网络找图、未登记文件或 filename 猜测成为 canonical candidate。

## 3. AssetCandidateSet

对每个 requirement 构建：

```text
AssetCandidateSet {
  asset_requirement_id
  candidate_asset_refs[]
  discovery_basis
  rejected_precheck_refs[]
  discovery_status
}
```

Candidate discovery 优先基于 structured metadata：

- semantic subject
- asset kind
- identity / appearance-state family
- locale
- capabilities
- provenance
- availability

Filename 仅可作为辅助 metadata，不是 identity proof。

## 4. Deterministic pre-filter

Python 可先排除：

```text
wrong media type
wrong semantic subject
wrong locale
unavailable / invalid
hash mismatch
provenance disallowed
known continuity mismatch
```

这些可直接标为 `PRECHECK_REJECTED`，无需 Qwen。

## 5. Compatibility status

正式使用：

```text
COMPATIBLE
COMPATIBLE_WITH_SUPPORT
PARTIALLY_COMPATIBLE
INCOMPATIBLE
INSUFFICIENT_EVIDENCE
```

`COMPATIBLE`：单 asset 满足所有 required capabilities 和 hard constraints。

`COMPATIBLE_WITH_SUPPORT`：可作为 complementary set 的合法成员，但自身不是完整解。

`PARTIALLY_COMPATIBLE`：满足部分要求，但 gap 尚未被验证为可由合法 combination 补齐。

`INCOMPATIBLE`：hard requirement / continuity / policy 等明确失败。

`INSUFFICIENT_EVIDENCE`：无法可靠判断，禁止硬猜。

## 6. Capability-level evaluation

每个 capability 逐项评估：

```text
SATISFIED
PARTIALLY_SATISFIED
NOT_SATISFIED
UNKNOWN
```

不能仅用单一 compatibility score 取代 hard constraints。

Score 最多作为 hard-compatible candidates 之间的 ranking hint。

## 7. AssetCompatibilityEvaluation

至少包含：

```text
evaluation_id
asset_requirement_id
candidate_asset_ref
capability_results[]
continuity_compatibility
release_compatibility
provenance_compatibility
availability_compatibility
overall_status
evidence_refs[]
evaluator_metadata
review_flags[]
```

Evaluation 必须 pin exact requirement revision/hash、asset revision/hash、policy/version 和 evidence refs。

## 8. AssetEvidence

正式引入：

```text
METADATA_EVIDENCE
VISUAL_INSPECTION_EVIDENCE
AUDIO_INSPECTION_EVIDENCE
CONTENT_HASH_EVIDENCE
PROVENANCE_EVIDENCE
HUMAN_VERIFICATION_EVIDENCE
DERIVATION_EVIDENCE
```

Evidence 必须 pin：

```text
asset_id
asset_revision
content_hash
```

Content hash 改变后，与 visual/audio content 相关的旧 evidence 不自动继承。

## 9. Visual inspection

当 trusted metadata 无法可靠证明 capability 时，应实际检查 image content，例如：

- face 是否可读
- full body 是否存在
- profile / three-quarter 是否可用
- wardrobe/state 是否匹配
- 是否多人/背景污染

Qwen/model inspection 可以作为 `MODEL_ASSESSED` semantic evidence，但不自动等价于 human/canonical verification。

已针对 exact content hash 获得的 intrinsic evidence可以复用，避免每次 resolution 重看同一 asset。

## 10. Audio inspection

Objective audio evidence 可包括：

```text
duration
sample rate
channels
file validity
silence / clipping
```

Semantic evidence可包括：

```text
speaker identity compatibility
language/locale usability
character voice compatibility
```

必须区分 objective facts 与 semantic judgment。

对 `VOICE_REFERENCE` 不验证“某句台词必须恰好 N 秒”；只有 `PREEXISTING_UTTERANCE_AUDIO` 才有 utterance-specific measured-duration compatibility。

## 11. Intrinsic / Contextual evidence

正式区分：

```text
INTRINSIC_ASSET_EVIDENCE
CONTEXTUAL_COMPATIBILITY_EVIDENCE
```

例如 `FULL_BODY=yes` 是 asset-centric；`matches Linsey school_uniform_A for PS018` 是 requirement-context-specific。

因此：

```text
asset capability evidence ≠ requirement compatibility
```

## 12. Cross-asset compatibility

Individual compatibility 不等于 set compatibility。

对 complementary assets 必须允许 `CrossAssetCompatibilityEvaluation`，检查：

- same character identity
- same hair / costume / age / injury state
- same location identity
- semantically relevant spatial consistency

两个 asset 单独 compatible，但联合引入 identity/state drift 时不得组成合法 set。

## 13. CandidateCombination

B6.3 可以构建 evaluated `CandidateCombination`：

```text
{Asset A, Asset B}
→ jointly covers required capabilities
→ COMBINATION_COMPATIBLE
```

但：

```text
CandidateCombination ≠ ResolvedAssetSet
```

组合发现使用 minimum sufficient strategy：先 hard-filter，再针对 capability gaps 构造最小互补组合，避免 brute-force subset explosion。

## 14. Ranking

在 semantic hard compatibility 通过后，可以按以下因素辅助排序：

1. required capability coverage
2. continuity compatibility
3. provenance trust
4. project canonical preference
5. preferred capability coverage
6. quality
7. reuse consistency

Semantic correctness 优先于 aesthetic preference。

`PROJECT_CANONICAL` 可在同等 fitness 下优先，但不能覆盖 hard incompatibility。

## 15. Human verification / trust

Evidence 可表达 trust source，例如：

```text
VERIFIED
TRUSTED_METADATA
MODEL_ASSESSED
UNVERIFIED
```

如果 policy 要求 primary character identity 使用 human verification，则 model-only evidence 不能自动升级为 VERIFIED。

## 16. No-compatible-candidate

Requirement 可能得到：

```text
NO_CANDIDATES
ONLY_PARTIAL_CANDIDATES
NO_COMPATIBLE_ASSET
```

进一步显式诊断：

```text
ASSET_CREATION_REQUIRED
CATALOG_EXPANSION_REQUIRED
METADATA_ENRICHMENT_REQUIRED
EVIDENCE_REQUIRED
```

Missing asset 不得 silent 降级 requirement。

B6.3 不负责生成图片/音频。

## 17. External asset ingestion

若 future policy 允许 external discovery，新 asset 必须先：

```text
discover
→ ingest/register AssetRecord
→ hash/provenance/availability
→ catalog revision
→ B6.1 context revision
→ B6.3 reevaluation
```

不能绕过 catalog 直接绑定。

## 18. Local validation

至少检查：

- evaluation targets valid requirement
- candidate belongs to pinned catalog universe
- asset hash matches
- evidence targets exact asset content
- COMPATIBLE 不得包含 hard-constraint failure
- combination 内部 cross-asset compatibility成立

## 19. Backend firewall

不出现：

```text
Picture N
H3 ref ordering
ComfyUI node
prompt / seed
backend ref limit
ProductionShot actual ref list
```

## 20. 冻结原则

1. B6.3 discovery + compatibility evaluation，不做 final binding。
2. 输出 `EpisodeAssetCandidateEvaluationPlan`。
3. Formal candidates 只能来自 pinned catalog universe。
4. Filename 不是 identity proof。
5. Python deterministic pre-filter。
6. Compatibility 五态正式固定。
7. Capability 逐项评估，hard constraints优先。
8. 正式使用 `AssetEvidence`。
9. Trusted metadata不足时应实际 inspect content。
10. Evidence pin exact content hash，content change 后不继承。
11. Intrinsic evidence 与 contextual compatibility 分离。
12. Model evidence不自动等于 human verification。
13. Complementary set需要 cross-asset compatibility check。
14. CandidateCombination 仍不是 final binding。
15. Combination 使用 minimum sufficient strategy。
16. Ranking 只在 semantic compatibility 后进行。
17. Canonical preference不能覆盖 hard failure。
18. No compatible asset显式 report，不降级 requirement。
19. B6.3 不负责 asset generation。
20. External assets 必须先 ingest/catalog。
21. Evaluations/evidence exact version/hash traceable。
22. B6.3 backend-agnostic。
