# v1.2 — User Direction / Revision Guidance（设计草案）

状态：**DRAFT ARCHITECTURE REFINEMENT — 待 review / freeze**

适用范围：

```text
v1.2-B creative / production stages

B1 Adaptation
B2 Structured Screenplay
B3 Production Planning
B4 Shot Planning
B5 Release Variant (future-compatible, not first implementation priority)
B6 Asset Resolution
B7 / Runtime only where the authoritative upstream contract explicitly permits
```

Authoritative existing architecture remains：

```text
A1–A6 = source-grounded story analysis
B1      = adaptation decisions
B2      = screenplay realization
B3      = production semantic requirements / staging / performance / continuity
B4      = shot / camera / composition / editorial planning
B5      = release variant
B6      = concrete asset resolution
B7      = deterministic execution compilation
```

本设计不是新的 pipeline stage，也不替代现有 B1/B2/B3/B4/B6 review + approval gates。

---

# 1. 产品目标

默认体验继续是：

```text
fully automatic
A → B → generation
```

用户不提供任何意见时，pipeline 必须能够从头到尾自动运行。

同时，在少数重要 creative / production 节点允许用户提供指导和修改意见：

```text
automatic by default
+
human steering when desired
```

用户可以指导：

- adaptation focus / compression / fidelity；
- 角色保留、强化、弱化；
- 人物外形；
- 发型；
- 衣着 / costume；
- visible appearance state；
- 台词；
- action；
- performance；
- staging / 人物空间位置；
- shot decomposition；
- camera；
- composition；
- frame-space positioning；
- concrete character/location/reference asset selection。

用户还可以针对已经生成的 exact artifact revision：

```text
review
→ give revision guidance
→ generate a new immutable revision
```

不得直接修改已经 APPROVED 的 canonical artifact。

---

# 2. Fundamental boundary — A6 remains neutral

A1–A6 不消费 creative user guidance。

例如用户说：

```text
“把红心皇后提前”
“Alice 改成短发”
“这一版不要爱情线”
“茶会部分大幅压缩”
“多用 close-up”
```

A6 仍然只回答：

```text
source story 是什么
角色/关系/剧情如何全局理解
```

而不因为 downstream creative intent 改写 GlobalStoryBible。

正式 creative steering 从 B1 开始。

因此：

```text
GlobalStoryBible
!=
User Creative Direction
```

# 4. Core objects

```text
UserDirection

```

---

# 5. UserDirection

`UserDirection` 表示 generation/revision 前已经存在的 user-authored creative intent。

概念结构：

```text
UserDirection {
  direction_id
  direction_revision

  origin
  category
  strength

  stage_scope
  target_scope
  target_refs[]

  instruction_zh

  supersedes_direction_refs[]
  status

  provenance
}
```

字段可在 implementation plan 中按现有 repo convention最小调整。

---

# 6. UserDirection origin

第一版至少：

```text
USER
```

未来如果允许系统生成建议：

```text
MODEL_PROPOSED
PROFILE_DEFAULT
DERIVED
```

必须与 USER 严格区分。

核心原则：

```text
model-proposed
!=
user requirement
```

Qwen 不得把自己的建议伪装成用户要求。

---

# 7. Direction strength

建议正式支持：

```text
MUST
MUST_NOT
PREFER
AVOID
```

含义：

## MUST

硬正向要求。

## MUST_NOT

硬禁止。

## PREFER

soft positive preference。

## AVOID

soft negative preference。

这比只有 MUST/PREFER/AVOID 更能明确表达：

```text
“不要爱情线”
“绝对不要更换 Alice 的视觉身份”
```

之类 hard negative constraint。

---

# 8. Direction status / lifecycle

UserDirection revision immutable。

建议 status：

```text
ACTIVE
SUPERSEDED
WITHDRAWN
```

修改方向时：

```text
direction rev N
→ new direction revision / replacement
→ old direction remains historical
```

禁止 in-place 改写已经参与过生成的 direction。

---

# 9. Stage scope

建议 stage scope至少：

```text
B1_ADAPTATION
B2_SCREENPLAY
B3_PRODUCTION
B4_SHOT
B5_RELEASE
B6_ASSET
```

一个 direction可以作用于多个 stage，但每个 stage只消费 deterministic projection得到的 relevant subset。

B7 默认不接受新的 creative semantics；它 deterministic compile approved upstream truth。

Runtime generation也不得成为 bypass upstream authority 的隐藏 creative editor。

# 12. Earliest authoritative owner rule

UserDirection 不能因为“用户要求”就绕过 stage ownership。

任何 direction必须路由到：

```text
earliest authoritative stage
that owns the requested semantic change
```

然后 downstream重新生成。

这是整个设计最重要的规则之一。

# 13. Story adaptation guidance → B1

例如：

```text
“减少茶会篇”
“强化柴郡猫”
“不要爱情线”
“红心皇后提前出现”
“结尾更温暖”
“更偏悬疑”
```

authoritative owner：

```text
B1
```

这些要求可以影响：

- ResolvedAdaptationTarget；
- AdaptationStrategy；
- SourceStoryDisposition；
- AdaptedStoryBeat；
- EpisodePartition。

不得在 B2/B3/B4偷偷实现一个本质属于 B1 的剧情改写。

---

# 14. Dialogue guidance → B2

例如：

```text
“Alice 台词短一点”
“不要大量旁白”
“疯帽子的语言更跳跃”
“这一场让 Cheshire Cat 多说两句”
“这一句换一种表达”
```

authoritative owner：

```text
B2
```

具体影响：

- SceneRealization；
- DIALOGUE；
- DialogueIntent；
- reaction / pause / minor realization。

如果用户要求的新台词改变 B1 adaptation truth：

```text
route B1
```

而不是让 B2越权。

---

# 15. Action guidance — B2 vs B3

“动作”必须区分两个层次。

## Story / screenplay action

例如：

```text
“Alice 走到桌边拿起钥匙”
“这里让角色先犹豫再离开”
```

如果它改变观众理解到的 dramatic action：

```text
owner = B2
```

## Performance / production realization

例如：

```text
“说这句时低头”
“走路更急”
“抬手指向门”
“动作更夸张”
```

如果不改变 screenplay truth，只改变 performance/staging realization：

```text
owner = B3
```

---

# 16. Character visual guidance has priority over shot guidance

产品 implementation priority明确冻结为：

```text
character visual / wardrobe / appearance guidance
>
shot / camera guidance
```

原因：

1. character identity / appearance continuity 会影响大量 downstream shots；
2. visual reference consistency 是 H3 generation 的核心输入；
3. camera guidance 可以在稳定 character visual semantics之后逐步增加；
4. 角色视觉要求不应该被临时 shot prompt反向定义。

---

# 17. Character visual semantics → B3

用户说：

```text
“Alice 改成短发”
“蓝白裙”
“这一段换成红色礼服”
“衣服有泥”
“头发湿了”
“角色脸上有擦伤”
```

首先不是 B6 concrete asset selection。

这些是：

```text
production semantic requirements
```

authoritative owner主要是 B3：

- WARDROBE；
- APPEARANCE；
- character presence；
- continuity；
- ProductionRequirement；
- ProductionRequirementUse。

因此：

```text
User visual direction
→ B3 semantic requirement
→ B4 shot planning consumes that truth
→ B6 resolves concrete assets satisfying it
```

---

# 18. Character visual identity vs appearance state

必须区分：

## Character visual identity

例如：

```text
Alice:
- short blonde hair
- recognizable face identity
- age presentation
- persistent base visual design
```

## Appearance state

例如：

```text
scene X:
- wet hair
- damaged dress
- dirt on face
- injury state
```

两者不能混成一个字符串。

B6 已经冻结：

```text
CHARACTER_VISUAL_IDENTITY
CHARACTER_APPEARANCE_STATE
```

本 guidance contract应直接与该边界兼容。

---

# 19. Wardrobe guidance → B3 semantics, B6 concrete asset

用户要求：

```text
“全片大部分时间保持经典蓝白裙”
```

首先形成 B3 wardrobe semantic requirement / continuity。

到了 B6：

```text
semantic wardrobe requirement
→ AssetRequirement
→ candidate evaluation
→ ResolvedAssetBinding
```

B6 不应自行重新解释用户原始服装意图。

---

# 20. Concrete visual asset guidance → B6

如果用户不是说“穿什么”，而是说：

```text
“我就要用这张 Alice face reference”
“这张图不要用”
“在这三个候选里选第二张”
“这套 costume asset 才是正确版本”
```

这是 concrete asset guidance。

authoritative owner：

```text
B6
```

可影响：

- HumanVerificationEvidence；
- compatibility evaluation；
- ResolvedAssetBinding；
- EpisodeResolvedAssetPlan。

不得直接把 filename/path塞进 B3/B4 semantic truth。

---

# 21. Missing visual asset

若 user semantic direction要求：

```text
short hair + blue/white dress
```

但 B6 catalog中没有满足 requirement 的 asset：

不得：

- silently pick wrong appearance；
- 改写 user direction；
- 让 B4 camera隐藏问题作为永久解决；
- 从 catalog外偷偷引用文件。

必须：

```text
asset requirement unresolved
→ route asset creation / import / registration workflow
→ new AssetRecord
→ B6 reevaluation
```

具体 asset-authoring workflow未来单独设计，不属于本 refinement。

---

# 22. Spatial position — B3 vs B4

“人物位置”同样分两层。

## Production-space / staging position

例如：

```text
“Alice 站在门边”
“Queen 在桌子另一侧”
“Cheshire Cat 在树上”
```

这是 scene/staging truth：

```text
owner = B3
```

可以进入 StagingDirective / production-space position。

## Frame-space / composition position

例如：

```text
“Alice 放画面左侧”
“Queen 居中”
“Cheshire Cat 出现在右上方”
```

这是 camera/composition realization：

```text
owner = B4
```

B4不能借 frame composition修改 B3的真实空间关系。

---

# 23. Shot / camera guidance → B4

例如：

```text
“红心皇后登场用低机位”
“这里用 close-up”
“减少大全景”
“用 OTS”
“这一场更偏手持感”
“保持 Alice 在 frame left”
```

authoritative owner：

```text
B4
```

映射：

```text
shot existence / split / merge
→ B4.2

scale / viewpoint / angle / composition / movement
→ B4.3

cross-shot continuity
→ B4.4
```

不得把 camera wording写回 B2 action或 B3 staging truth。

---

# 24. Shot guidance cannot override character visual truth

如果：

```text
B3 says:
Alice wears blue/white dress

B4 user direction says:
frame Alice in red dress
```

这不是 camera refinement。

必须：

```text
route B3
```

除非 user明确创建一个新的 B3 wardrobe exception。

B4不能拥有 wardrobe authority。

---

# 25. RevisionRequest

`RevisionRequest` 与 standing UserDirection不同。

它表示：

```text
human reviewed exact existing artifact
and requests a new revision
```

概念结构：

```text
RevisionRequest {
  revision_request_id

  target_artifact_ref
  requested_stage

  instruction_zh
  target_refs[]

  resulting_direction_refs[]
  reviewer_provenance
}
```

RevisionRequest immutable。

---

# 26. RevisionRequest exact target

RevisionRequest必须 pin：

```text
artifact_type
artifact_id
revision
content_hash
```

禁止：

```text
“修改最新 screenplay”
“把当前 shot plan改一下”
```

这种 implicit latest。

---

# 27. Review gate remains a gate, not editor

用户可以在 review UI 中输入：

```text
“这句对白太长”
“Alice 的衣服换掉”
“这个镜头换 close-up”
```

但 formal approval stage本身不得直接 mutate canonical artifact。

正确流程：

```text
review exact rev N
→ REVISION_REQUESTED
→ create RevisionRequest
→ route authoritative owner
→ produce rev N+1
→ validate
→ review / approve again
```

沿用 B1/B2/B3/B4/B6 frozen approval philosophy。

---

# 28. Standing direction vs one-off revision

例：

```text
“Alice 永远保持短发”
```

适合 standing `UserDirection`。

例：

```text
“只把 Scene 12 的裙子换成红色”
```

适合 target-specific UserDirection 或 RevisionRequest-derived direction。

例：

```text
“Shot 42 把 Alice移到画面左边”
```

属于 exact B4 revision guidance。

---

# 29. EffectiveUserDirectionSet

不建议每个 stage把整个项目所有 directions都塞给 Qwen。

Python deterministic 计算：

```text
UserDirectionSet
→ filter by stage/category/target/lifecycle
→ EffectiveUserDirectionSet
```

每个 stage只消费自己的 exact effective set。

例如 B2 不应该因为用户新增一条 B4 camera preference而 semantic reuse miss。

---

# 30. Effective direction identity

每个 stage semantic identity pin：

```text
effective_user_direction_set_hash
```

而不是整个 project UserDirectionSet hash。

因此：

```text
new B4 camera direction
→ invalidates B4 relevant output
→ does NOT invalidate B1/B2 by itself
```

这是避免 unnecessary recomputation 的关键。

---

# 31. Direction precedence

不得使用隐藏的“last text wins”。

第一版 precedence：

1. explicit supersession / withdrawal；
2. exact target-specific direction；
3. narrower scope may refine broader scope；
4. hard constraints vs soft preferences；
5. unresolved hard contradiction必须显式处理。

但：

```text
more specific
!=
automatically allowed to contradict a broader MUST
```

如果用户确实希望 scene-level exception覆盖 global MUST，应显式记录：

```text
supersedes / exception provenance
```

避免 silent contradiction。

---

# 32. Conflict handling

例如：

```text
global MUST:
Alice wears blue-white dress

scene MUST:
Alice wears red dress
```

若没有 explicit exception/supersession关系：

```text
DIRECTION_CONFLICT
→ fail/review before semantic generation
```

不要让 Qwen自行猜哪一条更重要。

---

# 33. User direction vs upstream approved truth

用户在 B2 review阶段要求：

```text
“让这个已经被 B1 omit 的角色回来”
```

B2不得照做。

route：

```text
B1 revision required
```

类似地：

```text
B4 user asks character to stand elsewhere
but that changes B3 staging truth
→ B3 revision required

B6 user asks for different costume semantics
→ B3 revision required

B6 user asks only for another concrete asset
with same approved semantic requirement
→ B6 revision only
```

---

# 34. Direction compliance

建议每个 guidance-aware stage都能够产生 lightweight：

```text
DirectionComplianceSummary
```

至少：

```text
satisfied_direction_refs[]
deviated_direction_refs[]
unresolved_direction_refs[]
```

对于 MUST / MUST_NOT：

```text
unsatisfied
→ BLOCKING
```

除非该 stage contract明确允许用户批准 deliberate divergence。

对于 PREFER / AVOID：

```text
unsatisfied
→ REVIEW_REQUIRED or WARNING
```

具体 severity由 stage implementation plan冻结。

# 35. Provider role

Qwen可以：

- 根据 UserDirection做 semantic proposal；
- 解释如何满足 direction；
- 判断 soft trade-off；
- 生成 revised screenplay/shot semantics；
- 比较 revision差异。

Qwen不得：

- 修改 UserDirection；
- 宣称用户要求了实际未要求的东西；
- silently discard MUST/MUST_NOT；
- 创建 target canonical IDs；
- 越过 stage authority。

# 37. Provenance

每个 downstream artifact应能解释：

```text
what came from source
what came from model
what came from user direction
```

必要的 output object可引用：

```text
direction_refs[]
revision_request_refs[]
```

例如某个 AdaptedStoryBeat因用户要求强化 Cheshire Cat 而新增，应能追踪到 exact direction。

---

# 38. Downstream invalidation matrix

## B1 semantic change

```text
B1 new approved revision
→ B2+ previous downstream lineage no longer current-eligible
```

## B2 semantic change

```text
B2 new approved screenplay
→ B3/B4/B5/B6/B7 downstream rebuild/revalidation
```

## B3 visual/staging semantic change

```text
B3 new approved production plan
→ B4/B5/B6/B7 downstream rebuild/revalidation
```

## B4 shot/camera change

```text
B4 new approved shot plan
→ B5/B6/B7 downstream rebuild/revalidation
```

## B6 concrete asset-only change

如果 B3/B4/B5 semantics不变：

```text
B6 new approved asset plan
→ B7 rebuild
→ B1–B5 remain unchanged
```

这一点非常重要。

---

# 39. Character visual change has two invalidation levels

## Semantic visual change

例如：

```text
long hair → short hair
blue dress → red dress
no injury → visible injury
```

owner B3：

```text
B3 revision
→ B4+
```

## Concrete asset substitution only

例如同一个 short-hair blue-dress requirement：

```text
asset A → asset B
```

且 semantic identity/appearance state不变：

```text
B6 revision only
→ B7 rebuild
```

不要把纯 asset substitution错误升级成 screenplay/shot rewrite。

# 42. Free-form text and structured control

User experience可以以 free-form text为主：

```text
“这场 Alice 的衣服换成红色，动作更紧张；
镜头不要 wide，尽量 close-up。”
```

但 persistence不应只是一个无结构 prompt append。

至少要明确：

- stage/category；
- target scope；
- strength；
- raw user text；
- exact target refs when available。

如果一句话跨多个 owners，UI/orchestration应拆分成多个 directions：

```text
WARDROBE → B3
PERFORMANCE → B3
CAMERA → B4
```

不得让一个跨-stage blob成为 hidden authority。

# 43. Natural-language routing

第一版可以采用两种输入模式：

## Explicit UI routing

用户在 B2/B3/B4/B6对应 review surface输入，stage/category由 UI已知。

这是最简单、最可靠的 v1。

## Future assisted routing

Qwen可以建议：

```text
this clause belongs to B3 WARDROBE
this clause belongs to B4 CAMERA
```

但模型只提议 routing。

Python/contract验证后才能形成 resolved direction。

不要让 routing model直接修改 canonical outputs。

# 45. Why visual guidance is implemented before shot guidance

人物视觉指导优先的理由：

- character identity consistency across shots is foundational；
- wardrobe/appearance continuity spans many shots；
- B4 should consume stable production visual truth；
- B6 concrete visual refs strongly affect H3 output identity consistency；
- camera refinements are easier once subjects are visually stable；
- avoids compensating for wrong character design with camera tricks。

因此：

```text
fix subject semantics/assets first
then refine camera realization
```

---

# 46. Interaction with B3 frozen ProductionRequirement

不引入 parallel `CharacterVisualSpec` authority unless implementation audit proves necessary。

优先复用 frozen B3：

```text
ProductionRequirement
CHARACTER
WARDROBE
APPEARANCE
ProductionRequirementUse
StagingDirective
PerformanceRequirement
```

如果未来需要 project-level persistent base character visual identity，可通过一个 narrowly-scoped reusable requirement/profile refinement设计，而不是复制一套与 B3/B6冲突的 character bible。

---

# 47. Interaction with B6 frozen asset model

User asset guidance必须走 existing：

```text
AssetRequirement
→ AssetCandidate
→ CompatibilityEvaluation
→ ResolvedAssetBinding
→ validation
→ approval
```

用户指定 concrete asset可以成为强 evidence/selection intent，但不能跳过：

- AssetRecord registration；
- content hash；
- compatibility；
- continuity；
- approval。

---

# 48. Human asset override is not arbitrary file injection

例如用户上传/指定一张新 Alice 图片：

不能：

```text
path
→ directly become Picture 1
```

必须：

```text
ingest/register AssetRecord
→ hash/provenance
→ requirement matching
→ B6 evaluation/binding
→ approval
→ B7 backend role/order
```

保持资产 firewall。

---

# 49. Approval interaction

UserDirection本身不是 approval。

RevisionRequest也不是 approval。

完整流程仍然：

```text
direction
→ generate/revise
→ validation
→ human review
→ approval
```

用户提出修改意见后不能自动把新 revision标记 APPROVED。

---

# 50. Reuse / semantic identity

每个 guidance-aware semantic stage必须把 exact：

```text
EffectiveUserDirectionSet identity
+
applicable RevisionRequest refs
```

纳入 semantic identity。

改变相关 guidance：

```text
→ reuse miss
→ new semantic generation
```

改变不相关 guidance：

```text
→ unrelated stage remains reusable
```

Runtime-only变化仍不影响 semantic reuse。

---

# 51. UserDirection persistence strategy

建议使用现有 immutable artifact store。

第一版可以是 project-level：

```text
UserDirectionSet
```

revisioned artifact。

每次修改 active direction set：

```text
new UserDirectionSet revision
```

Stage实际 pin deterministic `EffectiveUserDirectionSet` content hash/projection identity。

是否把 EffectiveUserDirectionSet本身持久化，implementation planning时根据 trace/debug价值决定；不需要现在强制第二个持久 authority。

---

# 52. RevisionRequest persistence

RevisionRequest必须 immutable persisted，因为它解释：

```text
why revision N+1 exists
```

例如：

```text
EpisodeScreenplay rev 3
+
RevisionRequest rr_0012
→ EpisodeScreenplay rev 4
```

这是 human provenance，不应只存在聊天记录。

---

# 53. Chat is not authority

未来 UI/agent可以让用户直接聊天：

```text
“这场她穿红衣服”
```

但聊天历史本身不能成为 production canonical authority。

必须 materialize 成：

```text
UserDirection / RevisionRequest
```

再进入 pipeline。

这样避免：

```text
“模型记得用户之前说过”
```

成为不可重现依赖。

---

# 54. Cross-stage compound guidance

如果用户一次说：

```text
“这一场 Alice 换红裙，台词更短，给她更多 close-up。”
```

应拆成：

```text
B3 WARDROBE
B2 DIALOGUE
B4 CAMERA
```

每条保留同一 parent user-submission provenance。

这样：

- owner清楚；
- invalidation清楚；
- reuse清楚；
- compliance清楚。

---

# 55. Direction granularity

第一版不要求用户每条意见手工拆成原子句。

可以保留：

```text
UserDirectionSubmission
```

作为 raw human text/provenance envelope，然后派生多个 UserDirection records。

但如果引入该 envelope会显著扩大 implementation，可第一版让 UI直接提交单 category direction。

核心是 production artifact不得依赖未解析聊天上下文。

---

# 56. No hidden prompt injection

禁止：

```text
system prompt
+ user text blob
+ “please follow”
```

然后不记录 identity/provenance。

正式 request rendering必须 deterministic：

```text
canonical upstream
+
exact effective directions
+
versioned prompt
→ request hash
```

---

# 57. Security / integrity boundary

User guidance可以改变 creative semantics，但不能要求 pipeline：

- 伪造 source provenance；
- 修改 immutable approved revision；
- 跳过 validation；
- 使用不存在的 artifact ref；
- 使用 catalog外未登记 asset；
- 绕过 approval；
- 修改 B7 compiled payload而不回 authoritative owner。

这些请求应被 route/refused by architecture，而不是“尽量执行”。

# 62. Definition of Done — architecture refinement

冻结本设计前至少确认：

1. A6 remains user-guidance-neutral。
2. UserDirection != RevisionRequest。
3. Chat/free text不是 production authority。
4. Stage ownership由 earliest authoritative owner决定。
5. B1拥有 adaptation guidance。
6. B2拥有 dialogue/screenplay-action guidance。
7. B3拥有 wardrobe/appearance/performance/staging/production-space guidance。
8. B4拥有 shot/camera/composition/frame-space guidance。
9. B6拥有 concrete asset selection/rejection。
10. Character visual semantics与 concrete asset分层。
11. Character visual/asset guidance implementation priority高于 shot guidance。
12. Review gate仍不是 editor。
13. User changes产生 immutable revisions。
14. EffectiveUserDirectionSet进入 stage semantic identity。
15. Unrelated guidance不应 invalidate unrelated upstream stage。
16. Hard direction conflicts不得 silent last-write-wins。
17. Downstream invalidation遵循 exact lineage。
18. Empty guidance保持现有 fully automatic behavior。
19. B7/runtime不成为 bypass upstream semantics 的 hidden creative editor。
20. No direct path/file injection绕过 AssetRecord/B6/B7 authority。

# 63. Decisions proposed for freeze

本草案建议最终冻结：

1. 增加 shared `UserDirection` / `UserDirectionSet` / `RevisionRequest` primitives。
2. A1–A6 不消费 creative guidance；B1开始。
3. 用户指导 optional；默认 full automation。
4. directions支持 stage scope + target scope + exact refs + category + strength。
5. hard strengths = MUST / MUST_NOT；soft = PREFER / AVOID。
6. stage只消费 deterministic `EffectiveUserDirectionSet`。
7. stage semantic identity pin effective direction identity，而不是整个项目所有 directions。
8. revision feedback exact-pin target artifact revision/hash。
9. approval stage不直接编辑 canonical artifact。
10. user request必须 route earliest authoritative owner。
11. dialogue / screenplay action owner B2。
12. character visual/wardrobe/appearance semantics owner B3。
13. concrete visual asset selection/rejection owner B6。
14. production-space position owner B3；frame-space composition owner B4。
15. shot/camera/composition owner B4。
16. semantic visual change从 B3向下 invalidates；pure B6 asset substitution只向 B7 invalidates。
17. character visual/asset guidance implementation priority高于 shot guidance。
18. user guidance不能绕过 validation/approval/provenance。
19. raw chat不是 authority；正式 guidance必须 materialize为 immutable artifact。
20. implementation按 shared primitives → B1 → B2 → B3 visual → B6 visual assets → B4 shot guidance推进。
