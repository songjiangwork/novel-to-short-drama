# B1.3-R0D1 — 审批认证契约提案

状态：**PROPOSED / NOT RATIFIED**。本文及其 PR 的创建、审查或合并都不是政策批准、身份建立、事故批准或 live invocation 授权；也不增加任何 Provider 预算。R0 和 [R0D](B1.3-operator-recovery-policy-decisions.md) 是背景和未批准的提案；#161 的合并不构成 ratification。Refs #170、#121。

## 分离的门槛

1. **架构 ratification**：经独立确认的人类项目权威明确接受或拒绝 R0D 的 A、B 及本契约。任一必需事项未决即 `NOT RATIFIED`；拒绝 A 则没有 R2 dispatch。批准本设计的机制不等于批准 A/B。
2. **身份与信任建立**：通过独立可信渠道确认权威及其凭据，固定验证所需的公钥、角色、政策摘要和撤销状态。签名只能证明密钥持有者签署了字节；身份与权限来自预先核实的绑定，而非签名者自报的名字、UID、Git SHA、`policy_reference` 或 PR。
3. **事故预审批与离线 preflight**：在零 Provider 条件下核验事故证据、权限与具体预算，产出可供人检查的完整冻结 preflight；必要的根初始化是独立审计事件，不是批准。政策批准不允许自动生成事故批准。
4. **最终 live authorization**：有权操作的人在审阅精确 preflight 和冻结证据后，对这一次具体 live invocation 明确签署独立授权，包括重复生成风险。preflight、GitHub review 或其他人的政策批准都不能代替此动作。
5. **持久 decision / consumption**：未来协议须在同一 guard 下重新验证上述所有门槛、证据及 checkpoint 缺失，持久化唯一 decision，随后不可逆地持久化唯一 consumption，成功验证后才能 dispatch。授权本身不等于 consumption；consumption 不证明请求已发出。本文不实现或启动这些步骤。

## 可信身份方案比较

| 方案 | 建立、验证与生命周期 | 边界和不足 |
| --- | --- | --- |
| **本地固定 Ed25519 公钥（有条件推荐）** | 项目权威通过预先约定的独立线下渠道核对完整公钥指纹及角色；将公钥、允许的政策文档 SHA-256、角色、有效期和撤销/轮换状态放进独立保护的本地信任配置，先于任何审批记录建立。用成熟库离线验证签名；操作员可使用单独的角色密钥，即使同一人承担两角色也需两次不同签名动作。密钥轮换或撤销须由预先认定的权威经独立渠道更新信任配置；旧签名在撤销后拒绝，轮换不会隐式继承未消费授权。 | 对单用户离线环境较小；但本机或私钥被攻陷、信任配置被替换、签名人被胁迫均不防护；不能证明人的实际理解或 Provider 没有处理旧请求。离线撤销状态可能过期：必须在每次授权/消费前以独立渠道确认可信配置是当前版本；无法确认则拒绝。 |
| **托管方身份证明（如 GitHub 签名/attestation）** | 预先通过独立渠道固定组织、账号、角色、签名身份及可信发行方；验证平台签名、证明的确切载荷、账号与授权映射、有效期及撤销状态，不能仅信任 PR review 或提交 SHA。轮换和撤销依赖平台及项目权威更新映射。 | 容易利用已有账号管理，但需信任平台、账号安全及证明格式，可能需要在线取得当前撤销信息；无可验证新鲜状态时离线拒绝。它不能证明账号背后的自然人、理解或实际 live 意图，也不能单凭合并证明批准。 |

推荐仅在人工选定权威、可信 bootstrap、当前撤销状态及本机威胁边界后采用第一种；是否接受单人持有两个角色密钥、凭据保管和恢复方式仍须决定。信任配置不能由审批文件、同一 PR 或其自报 key ID 引导；没有独立预置 trust anchor 或无法验证其当前性时安全地拒绝。私钥和秘密不进入仓库、审批记录或日志。时间有效性依赖可信时钟；时钟或撤销新鲜度不可信时拒绝。撤销和轮换对已消费记录不擦除历史，也不恢复预算。

## 拟议的不可变签名契约 v1

以下为未来实现的封闭契约，不是已有 R1 记录的实现或兼容性承诺。政策 ratification 与 live 授权使用两个不同类型的 envelope；后者引用前者的完整精确字节摘要。所有字段必填；明确标为 nullable 的字段才可为 JSON `null`，不得遗漏。未知字段、版本、类型、重复键、非规范字节或非法值均拒绝。字符串为非空 Unicode，摘要均为小写 64 位十六进制 SHA-256；整数为非负安全整数，禁止浮点。签名和公钥使用标准 base64，不含换行。时间为 UTC RFC 3339 秒精度 `YYYY-MM-DDTHH:MM:SSZ`；`issued_at <= now < expires_at`，可信时钟缺失则拒绝。

每个 envelope 为严格对象 `{ "payload": ..., "signature": ... }`，`signature` 是对 payload 的 Ed25519 签名；签名编码解码后恰为 64 字节。payload 和 envelope 均按 RFC 8785 JCS 生成 UTF-8 字节，无 BOM 或尾随换行，严格解析后必须字节级 round-trip。签名输入为 ASCII `B1.3-R0D1/approval/v1`、一个 `0x00` 字节、再接 JCS payload 的 UTF-8 字节；Ed25519 直接签这些字节，不预哈希。`envelope_sha256` 是完整 canonical envelope 字节的 SHA-256；引用和 preflight 的 digest 是原始精确字节 SHA-256，不能以重序列化结果替代。类型字段在签名范围内，阻止跨角色/用途替换。未来任何 schema、规范化或算法变更须采用新版本和 domain，不得宽松降级。

**共同 payload 字段**：`schema_version: 1`；`record_type` 为下述精确值；`key_id` 为已固定的 Ed25519 原始 32 字节公钥的 SHA-256；`issued_at`、`expires_at`；`policy_document` 为 `{path, version, sha256}`，摘要覆盖被批准政策文档的完整精确 UTF-8 字节，版本和路径须匹配独立信任配置。验证者用已预置公钥计算 key ID 并校验角色，不能从记录选择新的信任根。

**`policy_ratification` payload** 另含：`authority_id`（须匹配独立角色绑定）、`decision_a` 和 `decision_b`（各为 `approve` 或 `reject`）、`contract_version: 1`、`contract_document: {path, version, sha256}`（同样绑定本契约文档的精确 UTF-8 字节及独立信任配置）。A 的批准精确指 R0D 的 Alice `window_0001` 一次新增 invocation、每次至多 2 semantic rounds、每轮至多 3 technical attempts、合计至多 6 次新 Provider attempts，第二轮仅在 schema-valid semantic rejection 后；原使用量及完整 lineage 总数 UNKNOWN。B 的批准精确指 checkpoint v1 路径、codec、identity 不变，计数仅为该 invocation 的实际计数，且 consumption → terminal → 精确 checkpoint 身份/字节的完整审计是 reconciliation、acceptance、publication 前置条件。普通 claim 与无 consumption 的已验证初始化/decision 加已验证 checkpoint 仍是普通情况。若 A/B 任一拒绝或与受信政策内容不一致，不允许该恢复 dispatch。此记录不要求或声称知道将来 root inode。

**`live_authorization` payload** 另含以下字段；其每一项须与经独立验证的当前证据和受信 ratification 比较，而非仅互相比较记录中的 hash：

- `policy_ratification_sha256`；`operator_id`（须匹配独立预置的 live 授权角色）；`reason`；`incident_id`；`window_id: "window_0001"`、`window_ordinal`；`claim_identity`、`claim_bytes_sha256`（原始 canonical claim 的精确字节）。事故标识与 ordinal 必须匹配实际已验证 claim，不能凭提案推断。
- `preparation_identity`、`request_identity`、`semantic_request_hash`；`authority`：完整已验证 source snapshot 的精确 canonical bytes SHA-256，及 A5/A6 artifact refs（含 ID、revision、content hash）、A6 CURRENT pointer ref/revision/hash；B1.2 strategy ref/revision/hash、`selection_mode`（`CURRENT` 或 `EXPLICIT`）及 `current_pointer`（CURRENT 时完整 ref/revision/hash，EXPLICIT 时为 null）。这些嵌套对象的精确字段、类型及 nullable 规则须与未来冻结的 preflight schema 一并正式确定，未确定之前 v1 不可实施。所有 refs 均经既有 store/pointer 和 lineage 校验；任何 CURRENT 的变化均拒绝，EXPLICIT 不能假装 CURRENT。
- `roots`：execution、checkpoint、artifact、pointer 各自的 canonical absolute path、打开目录的 device、inode、file type；`checkpoint_parent` 同样绑定 path/device/inode/type；`root_result_identity` 和 `root_result_bytes_sha256` 在存在初始化 result 时均为其精确值，否则均为 null。若有 result，必须验证 intent/result 与当前 parent 和 root；新 inode 只表示恢复时状态，不表示历史状态。
- `caps`：`invocations: 1`、`semantic_rounds: 2`、`technical_attempts_per_round: 3`、`provider_attempts: 6`、`second_round: "schema_valid_semantic_rejection_only"`；`prior_usage: "UNKNOWN"`、`full_lineage_usage: "UNKNOWN"`；`attempt_id` 为独立生成的 128 位随机值的小写 32 位十六进制。唯一固定 claim 槽位和 durable consumption 才提供防重放，随机 ID 本身不提供防重放。
- `preflight_sha256` 为最终完整 canonical preflight 精确字节摘要；`ack_prior_requests_may_have_completed: true`、`ack_duplicate_generation_possible: true`、`authorize_specific_live_invocation: true`。这是一项明确的签署动作，不是默示确认。

preflight 须使用版本化、封闭、canonical 格式，包含上述所有证据值、ratification envelope 摘要、operator、reason、attempt ID、检查结果、checkpoint 缺失和预算；不含 live envelope 或其摘要以避免循环引用。先冻结并展示完整 preflight 供人审阅，再生成引用其精确摘要的 live envelope。未来协议必须规定有界大小和受信配置分发、规范化实现及可复现测试向量，未完成前不能实施。对于原始历史，Qwen server task IDs 196374/198243 只是可能匹配，不是经认证的 client request ID 或调用次数证据。

## 验证、持久化与对抗矩阵

未来 verifier 必须从独立受保护且已确认当前的信任配置取得期望的政策文档 digest、公钥和角色；加载精确政策文档与两个 envelope，检查字节规范、签名、角色、批准选项、有效期与撤销，再重建并验证实际 session、claim、authority、roots 和 preflight。有效签名只是必要条件；它不证明 ratification 有效，更不单独授权执行。所有检查在 guard 下重新执行，且在不可逆 consumption 前和 dispatch 前重新确认。若改变需要新 preflight 和新明确授权，也不能绕过固定槽位或已消费状态。

| 情况 | 必须的结果 |
| --- | --- |
| 缺少审批、签名无效、未知/未受信签名者、角色不符、缺少可信 bootstrap、过期、撤销/轮换或撤销状态不新鲜 | 拒绝 dispatch，即使另一签名有效 |
| 签名有效但 claim 字节/身份、window、preparation、request 或 source authority 不符；B1.2 模式、strategy 或 CURRENT pointer revision 不符 | 拒绝 dispatch；重新核验真实引用，不接受自洽的伪造 hash |
| checkpoint 出现或存在已验证 checkpoint | 零 dispatch，checkpoint 优先复用；无 consumption 且证据完整时按普通审计，有 consumption 时必须完成恢复 lineage 审计，异常/不完整阻止下游权威使用 |
| root、result 或 parent 缺失、替换、不匹配；preflight 后证据或预算改变 | 拒绝 dispatch；不得采用新 inode 或扩大预算 |
| 重复/冲突 decision、已消费记录、相同 attempt 重放、terminal 已存在 | 拒绝新的 dispatch；已有相同 decision 只可检查，不能创建第二个 decision 或绕过 consumption |
| partial record、no-clobber 冲突、link/文件或目录 fsync/最终验证不确定、可疑临时残留 | 拒绝 dispatch；不自动清理或把不确定视为缺失，单独只读调查 |
| 旧 Provider attempts 数量或结果模糊 | 不推断为零或剩余预算；无明确批准的 A、独立 live 授权及其他全部门槛时拒绝 dispatch；即使具备这些门槛也仅允许 A 的新增上限 |

R0 的固定 per-claim 槽位、no-clobber、文件及目录 fsync、guard 和 checkpoint 优先规则仍适用。未来 decision 必须绑定两个 envelope 的精确字节摘要、preflight 摘要和同一 attempt ID；consumption 必须绑定该 decision 和相同 attempt ID。decision 和 consumption 均须在当前 guarded 操作中成功持久化并精确验证；consumption 一旦存在或其持久性不确定，禁止重试，即使崩溃发生在网络调用之前。terminal 缺失为 outcome unknown；完整 recovered lineage 才能通过下游审计。现有 R1A/R1B1/R1B2/R1B3 的离线 codec/inspector、decision storage 和 root initialization 不认证此签名契约，`policy_reference` 匹配不证明批准，也没有实现 consumption 或 dispatch。现有普通 runner 对 unresolved claim 继续 fail closed。

## 人工 ratification 清单

以下任一未完成或无法独立验证，状态均为 **NOT RATIFIED**：

- 明确有权批准架构的自然人/项目角色及独立身份核验方式；确认谁可签发具体 live authorization，以及是否允许同一人承担两角色。
- 指定待批准的政策文档路径、版本及其精确 SHA-256，明确逐项批准或拒绝 A、B，以及本认证契约的确切版本；不能仅批准 PR 或引用 Git SHA。
- 决定信任机制及安全 bootstrap、固定公钥/角色/政策 digest、私钥保管、可信时钟、撤销状态新鲜度及离线不可用时的处理；决定轮换、撤销、丢钥与恢复责任。
- 明确版本迁移、撤回/回滚和未消费授权失效规则，以及谁有权执行这些动作；不能通过撤回或轮换重置已消费预算。
- 决定记录大小、保留期限、安全失败代码及 preflight 完整格式；审查未来实现的测试和威胁边界。
- 对本事故另行检查精确证据、风险与预算，并由有权操作的人单独作出具体 live 签署；任何新增 Provider 预算均不会由本提案自动批准。

只有分别记录人工 ratification 与 trust-anchor bootstrap 后，才可考虑另开有界、零 Provider 的 R2 preflight/consumption-design issue；实际 live 调用还须独立授权及后续实现和审查。本文不构成这些动作。
