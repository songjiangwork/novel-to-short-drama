# B1.3 Alice failure forensics (issue #121)

The 2026-10-27 `window_0001` execution has a verified unresolved claim for request identity `504656656d9a228c2cbb31c82256ad691b65e0376ae24ae0695a37503d07d220`, and no checkpoint. The CLI reported FAILED after approximately 24 minutes. Qwen tasks 196374 and 198243 are highly probable matches: both report 28,652 prompt tokens and about 6,000 generated tokens, with no server-side truncation; independent preflight measured 28,676 prompt tokens. These are matching indicators, not persisted client exception evidence. They do not establish the number of semantic rounds or all client attempts. The old CLI emitted only a failure phase and explicitly set in-flight counts to null; rejected-round evidence is retained in a checkpoint only after an accepted proposal. No exception or rejected proposal is recoverable from the claim.

After the claim, a completed server task need not correspond to a successfully received, parsed or validated client response. The following paths can leave no checkpoint:

- A response can be lost, time out or fail at HTTP/transport level on the client. Malformed response envelopes, empty or invalid JSON, local schema failure, or provider-reported length truncation are adapter failures. Retryable failures can consume up to three technical attempts per semantic round; exhaustion chains the last failure. A server-completed response does not rule out a client-side failure.
- After a structured result, invalid attempt accounting, authority revalidation, provenance checks, B1.3 schema decoding, or unexpected exceptions can abort. Provenance failure does not initiate semantic regeneration. The authority check precedes provenance and proposal acceptance.
- A schema-valid B1.3 proposal rejected by semantic validation consumes a round; a second rejection exhausts the two-round policy. A rejection followed by any of the other failures also leaves no checkpoint. The second semantic round disables prompt context reuse; adapter technical retries are separate and do not consume a semantic round.
- After acceptance, guard/root or authority/resume-plan revalidation, checkpoint encoding/evidence verification, filesystem operations, or other exceptions can fail before the checkpoint is saved. A failure during or after atomic linking or directory sync can also leave a checkpoint present but with uncertain durability; failure status alone does not prove absence. Process interruption and non-Exception termination can leave an unresolved claim without a CLI summary.

Two matching server tasks are consistent with two semantic rejections, or with technical retries after malformed/invalid structured responses, or with a mixture (including one semantic rejection then a technical failure). They are also consistent with a provenance or other post-response failure on a later successful client result after a prior technical retry or semantic rejection. Provenance failure by itself does not request a second response. Parsing/schema failure may trigger technical retries in the adapter; a B1.3 schema error after the adapter returns fails immediately. The logs do not distinguish these scenarios, and absence of server-side truncation does not establish local parsing or semantic validity.

The CLI now emits one fixed `error_code` on failure. It classifies known exception types at explicit boundaries, unwrapping only the runner and adapter retry-exhaustion wrappers. For exhausted technical retries the code identifies the **last** technical error, not every attempt. Malformed response envelopes and structured/schema failures share `STRUCTURED_OUTPUT_FAILURE`; unclassified failures use `UNKNOWN_FAILURE`. Authority revalidation has a dedicated subtype; checkpoint storage errors are identified by their storage subtype. Evidence or guard failures without a specific safe type remain unknown. No exception text, class name, response or source content is reported. Failed live-run counters remain null because the runner does not provide complete trusted accounting on failure. These diagnostics are prospective; they cannot reconstruct this incident.

## Recovery design recommendation (not implemented)

Keep the original immutable claim and any checkpoint or provider evidence intact. Design a separate operator-only, audited recovery record bound to the exact claim, request, roots and authority snapshot, with a unique decision ID, operator identity, timestamp, reason, and references to reviewed evidence. Under the existing exclusive execution guard, revalidate the claim, checkpoint absence or exact evidence, current authority and prior recovery decisions; require an explicit decision and a durable, atomic audit record before authorizing a new attempt. A single-use authorization must prevent concurrent or repeated replay, and should record the new attempt as a distinct lineage linked to the original claim. The operator must explicitly acknowledge that a prior provider task may have completed and that duplicate execution cannot be ruled out. Any ambiguity, changed authority, incomplete audit write, or conflicting recovery decision fails closed. This recommendation does not authorize recovery or replay of the existing claim.
