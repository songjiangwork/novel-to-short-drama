# B1.3-R0D — Recovery policy and audit decision proposal

Status: **PROPOSED / NOT RATIFIED**. Based on [B1.3-R0 operator recovery architecture](B1.3-operator-recovery-architecture.md) (merged as PR #160, merge commit `be6ecee9622c2beedb04ba69dc68b2bfc129c639`). Refs #121.

This document recommends explicit choices for two R0 decision gates. It is not itself an approved exception, an operator authorization, or a live-run procedure. **Do not dispatch the Provider, consume an authorization, create recovery execution artifacts, or modify the original claim by merging this proposal.** Production implementation of the dispatch path requires separate approval of these decisions, tested enforcement and a later incident-specific operator action.

## 2. Decision A — proposed one-time bounded exception

**Proposal for explicit architecture approval:** allow one narrowly bound recovery *invocation* for this specific unresolved Alice claim only, as an exception to the conservative lineage-wide two-round interpretation. It is **not** remaining budget from the original attempt and is **not** a modification of the ordinary B1.3 runner.

| Quantity | Proposed recovery policy |
| --- | --- |
| Original lineage semantic rounds / Provider attempts | UNKNOWN; never treated as zero |
| Number of newly authorized recovery invocations | At most **one**, by explicit durable single-use consumption |
| Maximum semantic rounds within that invocation | **2** (proposal then at most one semantic regeneration) |
| Technical attempts per semantic round | At most **3**, following existing retryable-error rules |
| Total new Provider attempts | At most **6** |
| When a second semantic round is allowed | Only after a schema-valid B1.3 semantic rejection |
| After consumption crashes, errors or uncertain outcome | Spent; **no automatic retry or second authorization** |
| After a complete recovered checkpoint | Verified reuse only; separate recovery audit gate still applies |
| Full lineage cumulative totals | UNKNOWN unless exact evidence later proves them |

This is a tightly scoped exception, not a general claim-reset ability. The policy must bind exact original canonical claim bytes/hash, preparation and request identities, A5/A6 and B1.2 authorities, trusted execution/checkpoint roots and a distinct attempt ID. Wrong window, changed authority, new root identity, corrupt evidence, or missing approval must fail closed.

**Approval gate:** a human project authority must explicitly ratify the exception in a separately reviewable record tied to the approved policy text and incident; a CLI flag, environmental variable, operator acknowledgment, drafted document or Git merge alone is not sufficient. A later, separate, explicit operator authorization for a specific live invocation is also required. The actual authentication/trust mechanism must be settled and tested before R2 dispatch code; until then there is no dispatch authority.

## 3. Decision B — proposed checkpoint-v1 compatibility + mandatory audit gate

**Proposal for explicit architecture approval:** preserve the existing immutable B1.3 checkpoint v1 codec, path and checkpoint identity. Its round/attempt counters represent the *invocation that produced the accepted proposal*, not the unknown earlier failed attempt or entire recovery lineage. Reconcile inaccurate cumulative-window comments before implementation; never rewrite, silently relabel, or fabricate historic counts.

Keep the recovery lineage in separate bounded, canonical, immutable no-clobber records in the existing execution root (guarded checkpoint-root initialization intent/result when applicable, approved policy binding, decision, consumption, terminal linked to checkpoint identity and canonical checkpoint byte hash). The accepted proposal must contain the actual recovered invocation's verified provenance and internally consistent bounded counts; null unknown counts belong in audit records, not invented into a checkpoint that requires integers.

Classify **only after exact claim, checkpoint and recovery-slot inspection**, with the following behavior:

| Situation | Recovery audit result | Dispatch | Downstream authoritative use |
| --- | --- | --- | --- |
| Valid ordinary checkpoint + retained original claim, no recovery evidence | ORDINARY_AUDIT | Forbidden | Allowed subject to ordinary gates |
| Valid checkpoint + verified initialization and/or decision only, no consumption and no ambiguity | ORDINARY_AUDIT; report pre-dispatch activity | Forbidden; decision cannot be consumed after checkpoint | Allowed subject to ordinary gates |
| Valid checkpoint + verified consumption + complete linked terminal/lineage | RECOVERY_AUDIT_COMPLETE | Forbidden | Allowed subject to all other gates |
| Valid checkpoint + consumption + missing/mismatched terminal or incomplete lineage | AUDIT_INCOMPLETE | Forbidden | **Blocked** |
| Valid checkpoint + malformed, conflicting or uncertain recovery evidence | AUDIT_INCOMPLETE | Forbidden | **Blocked** |
| No verified checkpoint + original unresolved claim | BLOCKED for ordinary runner | Forbidden without separately approved recovery protocol | Not available |

A normal successful execution retains its immutable claim, so claim presence alone **cannot** indicate recovery. Consumption indicates only that a recovery attempt *may* have dispatched, never that it definitively did.

Any recovered checkpoint must pass the added audit gate **before B1.3 reconciliation or any downstream authoritative consumption**, including acceptance/publication. The existing checkpoint verifier may still return valid semantic evidence and enable no-generation reuse when audit is incomplete, but no downstream acceptance may label it audit-complete. No missing, invalid or contradictory sidecar authorizes a new generation.

## 4. Durable authorization, root initialization and threat boundary

R0's guard and crash-consistency rules are normative design constraints, conditional on ratification:

1. Retain original claim, protect trusted fixed roots and acquire the existing exclusive execution guard; never replace/rename/relocate/delete claim or checkpoint.
2. If the checkpoint root is absent, any creation is a separately recorded, guard-held final-component private initialization with no-follow checks, trusted parent and parent fsync. A new inode is **recovery-time identity**, not a historical claim about the failed dispatch. Initialization cannot authorize Provider calls.
3. Verify fresh runtime/tokenizer/prompt/schema/budget and A5/A6/B1.2 authorities plus exact claim and all recovery records before each irreversible transition.
4. The operator decision and its matching single-use consumption must be durably published and verified before dispatch. Once consumed, crash before the first request still spends the attempt.
5. Success uses the existing exact checkpoint verifier and no-clobber save, followed by a uniquely bound terminal record. Failed or uncertain writes block; no auto-cleanup, replay, or claim reclamation.
6. A valid checkpoint takes precedence over recovery records for **zero-dispatch** decisions; recovery audit completeness remains a separate check.
7. Filesystem hashes/UIDs and Git references are evidence and local trust anchors, **not** cryptographic proof of a named operator's identity. Do not claim authenticated approval until its mechanism has been specified and tested. Locking is cooperative and does not protect against privileged or non-cooperating mutations.

## 5. Implementation and acceptance gates

- **R1 (permitted to design/test without ratifying dispatch):** strict standalone recovery record codec/verifier and read-only inspector, zero Provider client; fixed per-claim slots, bounded canonical JSON, cross-reference validation, clean absence vs incomplete/corrupt/uncertain state, guarded filesystem invariants, fake-client and fault-injection tests. No consumption publishing and no automatic creation of real Alice roots.
- **R0D ratification (separate explicit decision):** approve/reject the single additional invocation, checkpoint-v1 invocation-local accounting and downstream audit rules, policy-approval mechanism, operator authentication assumptions, record size/retention caps and exact failure allowlist. Reviewable evidence must identify the frozen policy version and approval authority.
- **R2 (only after ratification):** a separate guarded operator recovery entry point, durable decision/consumption, precisely one bounded execution and verified checkpoint/terminal integration. Ordinary CLI never bypasses claim protections.
- **Incident live run (later, separate explicit operator approval):** one-window bounded execution with a fresh read-only preflight, verified decision and root evidence, explicit duplicate-risk acknowledgment, secure logs and post-run audit. A successful checkpoint is not B1.3 reconciliation, human approval or publication.
