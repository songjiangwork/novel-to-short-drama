# B1.3-R0D3 — 离线审批与 preflight wire contract

状态：**SPECIFICATION PROPOSAL / NOT RATIFIED**。Refs #173、#172、#121。用户认为 [R0D A/B](B1.3-operator-recovery-policy-decisions.md) 的方向可接受，但这不是经过认证的 ratification，R0D 和 R0D1 仍为 **PROPOSED / NOT RATIFIED**；本文不批准 Alice 恢复、Provider 预算或 live invocation。本文是 [R0](B1.3-operator-recovery-architecture.md)、[R0D](B1.3-operator-recovery-policy-decisions.md)、[R0D1](B1.3-r0d-approval-authentication-proposal.md) 的未来精化，不改变 [Alice acceptance plan](B1-alice-acceptance-plan.md)。没有访问真实 Alice roots、创建密钥或记录、签名或调用 Provider。所有下述格式均为提案，现有 R1 不支持它们。

## 编码和共同类型 v1

所有对象封闭：表中列出的键全部必填，除明确 `?` 可为 JSON null 外均不可为 null；禁止未知键、重复键、非法 Unicode、BOM、尾随空白、浮点、负数及超出范围的整数。字符串限制按 UTF-8 字节计，拒绝控制字符；不进行 Unicode 归一化。`S` 为 1–256 字节字符串；`P` 为 1–4096 字节规范绝对路径，必须与安全打开的真实路径一致、无符号链接或 `.`/`..` 分量；`H` 为 64 位小写十六进制 SHA-256；`U` 为 0–9007199254740991 整数，`U+` 为 1–9007199254740991；`T` 为严格合法 UTC `YYYY-MM-DDTHH:MM:SSZ`；`B64(n)` 为标准 padded base64、无空白且规范重编码后解码恰 n 字节。`ID` 为 1–128 字节 ASCII `[A-Za-z0-9][A-Za-z0-9._:/@+-]*`；`attempt_id` 为独立随机 128 位、32 位小写十六进制；这些 ID 不是人的身份凭证。数组按表列限制，顺序有意义，禁止重复元素或重复 key ID。

每个制品使用 RFC 8785 JCS UTF-8，无尾随换行。先有界读入原始字节，严格解析并验证类型，再以 JCS 重编码，要求与原始字节完全相同。摘要始终是原始完整 canonical 字节的 SHA-256，不以重编码代替原件。preflight 上限 65536 字节；各签名 envelope 上限 32768 字节；manifest envelope 上限 65536 字节。所有限制包括包装及签名。现有 R1 的 `content_hash` 是其自身 codec 定义的身份，不自动等于文件字节 SHA-256。

签名 envelope 恰为 `{payload, signature}`，`signature: B64(64)`。审批的 Ed25519 原始签名输入是 ASCII `B1.3-R0D1/approval/v1` + 单个 `00` 字节 + JCS payload；不预哈希，`record_type` 在签名内区分用途，与 R0D1 一致。manifest 的域为 ASCII `B1.3-R0D3/trust-anchor-manifest/v1` + `00` + JCS payload。引用 envelope 的 H 覆盖整个 envelope，包括签名；preflight H 覆盖其完整原始字节。算法或字段变更须新版本及 domain，禁止降级。签名、公钥必须严格校验，不能接受非规范编码。

以下命名对象均仅有表中字段：

| 类型 | 封闭字段及约束 |
| --- | --- |
| `Document` | `path: S`（仓库相对路径、无 `.`/`..`）、`version: ID`、`sha256: H`（完整精确文件字节） |
| `Ref` | `artifact_type: ID`, `artifact_id: ID`, `revision: U+`, `content_hash: H`；来自已验证 store 的精确 artifact/pointer identity，不是自行声称的文件哈希 |

## 四个制品

### policy_ratification envelope

payload 封闭字段：`schema_version: 1`, `record_type: "policy_ratification"`, `key_id: H`, `authority_id: ID`, `issued_at: T`, `expires_at: T`, `policy_document: Document`, `contract_document: Document`, `scope: Scope`, `decision_a: "approve" | "reject" | "defer"`, `decision_b: "approve" | "reject" | "defer"`。`key_id` 是固定 Ed25519 原始 32 字节公钥的 SHA-256；authority_id 必须等于独立 manifest 的角色绑定。`issued_at <= now < expires_at`，且记录有效期位于签名密钥与 manifest 有效期内。仅 A、B 均为 approve 才可继续；reject/defer 是明确非批准。R0D1 列出 approve/reject；这里显式增加 defer 作为非授权结果，是待审 schema 提案，不改变 R0D1 的授权语义。

A 的精确范围是 R0D 的一次新增调用及 `Caps`；B 是保留 checkpoint v1 codec/path/identity、仅记录新增调用计数，以及消费 → terminal → checkpoint 精确身份和字节的完整审计门槛。`scope` 必须由独立证据验证，包括原 claim canonical 原始字节及其 preparation/request 关联；不得填入未知 Provider 历史或未来 root inode。政策和契约的路径、版本、精确文件摘要须均匹配 manifest allowlist 与本地验证的文件。合同 document 指本 R0D3 的精确版本；是否还须独立列出 R0D1 digest 是 **OPEN DECISION**，在解决并完成版本审查前不得部署。

### preflight v1

完整对象封闭字段如下，零 Provider 离线检查、供人审阅并冻结，不包含 live envelope 或其摘要。用于新 invocation 的 baseline 是签署时不可变的精确字节和 hash；它记录写入 decision 前的状态，不是后续实时状态的替代品：

| 字段 | 类型与约束 |
| --- | --- |
| `schema_version`, `record_type`, `created_at` | `1`, `"preflight"`, `T`；必须不晚于可信 now 且不早于 ratification 的 issued_at，不自行产生授权 |
| `policy_ratification_sha256`, `scope`, `operator_id`, `reason`, `attempt_id` | `H`, `Scope`, `ID`, `S`, `attempt_id`；scope 与 ratification 及独立原始证据逐字段相等 |
| `claim` | `{file: File, state: "CLAIMED_UNRESOLVED"}`；file 字节哈希等于 scope，原 claim codec 验证 identity、语义及精确路径 |
| `authority`, `roots`, `root_result` | `Authority`, `Roots`, `RootResult?`；result 为 null 仅当核验无初始化记录且已有可信 root；若初始化存在必须验证 intent/result 及字节身份 |
| `checkpoint` | `{status: "ABSENT", expected_path: P}`；准确槽位和可信 root 下只读证实缺失；任何有效 checkpoint 优先复用，损坏或不确定也不视为缺失 |
| `slots` | `{root_intent: Slot, root_result: Slot, decision: Slot, consumption: Slot, terminal: Slot}`；`Slot` 封闭为 `{status: "ABSENT" \| "VERIFIED", identity: H?, bytes_sha256: H?}`。ABSENT 两 hash 为 null；VERIFIED 两者均为 H，精确读取并按 R1 codec 校验。intent/result 必须成对；`root_result` 为 null 当且仅当这两个槽位均 ABSENT，否则其 identity 和 bytes_sha256 必须逐项等于 result 槽位，并验证 result 对 intent identity 的引用；新 invocation 的 baseline 中 decision、consumption、terminal 均必须为 ABSENT；任何残留、冲突或不确定拒绝。已有 decision 只允许只读调查，不能创建可用于新 invocation 的 preflight；`EXISTS_VERIFIED` 不构成授权。 |
| `runtime` | `Runtime`，如下；实际新鲜发现并重建，不能凭此文填值 |
| `caps`, `acknowledgements` | `Caps`, `Acknowledgements`；是审阅提示，不代表签署同意 |

`Runtime` 封闭字段：`observed_at: T`, `provider_config_id: ID`, `provider_config_sha256: H`, `model_id: ID`, `model_config_sha256: H`, `tokenizer_id: ID`, `tokenizer_sha256: H`, `effective_n_ctx: U+`, `input_ceiling_tokens: U+`, `reserved_output_tokens: U+`, `estimated_input_tokens: U+`, `provider_request_bytes: U+`, `profile_id: ID`, `profile_sha256: H`, `prompt_id: ID`, `prompt_sha256: H`, `schema_id: ID`, `schema_sha256: H`, `semantic_request_hash: H`, `rendered_prompt_sha256: H`, `packet_sha256: H`, `budget_result: "PASS"`。配置摘要覆盖各自完整、无秘密的规范化配置证据；具体配置证据 codec 和可信发现接口是 **OPEN DECISION**，未定义前拒绝实际验证。不得将凭据或 endpoint secret 纳入记录。必须重算实际 packet/request、tokenizer 测量和预算，`estimated_input_tokens <= input_ceiling_tokens`，并验证输入加预留输出不超过 `effective_n_ctx` 及现有全部 profile 限制；不可截断。冻结的 scope/authority/claim 是不可变语义身份；runtime 是时点证据，必须消费前及 dispatch 前重新发现并逐项比较，不能覆盖 request identity。独立证据发生不允许的变化即拒绝；只有固定槽位仍允许新 invocation 时才可另行冻结 preflight 并取得新 live 签署，已有 decision 不可因此复用；已消费或可能消费时禁止重试。

以上事实要求未来在实际受信环境只读检查；本文没有生成任何实例、虚构 hash 或声称探测过 Alice。预先存在的初始化是独立审计事件，不由 preflight 创建。可信时钟、root 状态及 CURRENT 也必须在 guard 下重新检查；锁仅保护合作进程，不能防御特权篡改或 ABA。

### live_authorization envelope

payload 封闭字段：`schema_version: 1`, `record_type: "live_authorization"`, `key_id: H`, `operator_id: ID`, `issued_at: T`, `expires_at: T`, `policy_ratification_sha256: H`, `preflight_sha256: H`, `scope: Scope`, `reason: S`, `attempt_id: attempt_id`, `authority: Authority`, `roots: Roots`, `root_result: RootResult?`, `caps: Caps`, `acknowledgements: Acknowledgements`, `authorize_specific_live_invocation: true`。签名 key/操作员须有独立预置的 live-authorizer 角色，时间规则同 ratification。所有重复字段逐字段与冻结 preflight、ratification 和独立核实证据比较；hash 引用完整精确 envelope/preflight。签署是审阅后独立明确 opt-in，不可从 ratification、凭据或 preflight 推断；不同角色是否允许同一人仍为 **OPEN DECISION**。随机 attempt ID 本身不防重放。

### trust_anchor_manifest envelope

manifest 不由审批 envelope 或仓库自行引导。独立带外 bootstrap 预先固定 manifest root 公钥及其完整指纹、验证域、信任来源、最新版本/撤销信息和可信时钟；manifest 签名用该预置 root 验证，绝不能用 manifest 自带 key 自签引导。离线时无法独立确认当前版本或撤销新鲜度则拒绝。bootstrap 的渠道、根密钥保管、可信时钟及 freshness 证明是 **OPEN DECISION**，下面字段不自行建立信任。

payload 封闭字段：`schema_version: 1`, `record_type: "trust_anchor_manifest"`, `root_key_id: H`, `manifest_version: U+`, `issued_at: T`, `expires_at: T`, `revocation_checked_at: T`, `revocation_valid_until: T`, `bootstrap_provenance_ref: ID`, `keys: Key[]`（1–32）, `allowlist: Allow[]`（1–32）。`Key` 封闭为 `{key_id: H, public_key: B64(32), principal_id: ID, role: "policy_ratifier" | "live_authorizer", not_before: T, not_after: T, status: "active" | "revoked", revoked_at: T?}`；key ID 必须等于原始公钥 SHA-256，active 的 revoked_at 为 null，revoked 的为非 null 且不晚于可信 now。每 key ID 唯一；两角色使用独立 key。`Allow` 封闭为 `{policy_document: Document, contract_document: Document}`，组合唯一。每个 Key 必须满足 `not_before < not_after`，manifest 必须满足 `issued_at < expires_at`，且审批记录必须满足 `issued_at < expires_at`。根 key ID 必须匹配预置 root，而非仅匹配 payload。

要求 `issued_at <= revocation_checked_at <= now < revocation_valid_until <= expires_at`，`issued_at <= now < expires_at`，签名 key 在 `not_before <= now < not_after` 且 active。独立渠道确认 manifest_version 为当前版本及 freshness，防回滚；无法确认即拒绝。轮换需带外确认新 root 或由已预置 root 签发更新并经独立渠道确认当前版本；旧授权不自动继承，撤销后的签名拒绝。已消费历史不能因轮换/撤销重置。撤销传播时限、root 轮换/丢失、旧未消费授权撤回、保留期限及跨角色同人策略均为 **OPEN DECISION**；现有字段不解决这些运营问题。

## 验证顺序与未来状态转移

以下验证步骤只读，任一步失败即 DENY；不从自洽 hash 推断真实身份。表中的持久化是未来 R2 的拟议转换，本文不实现它们：

1. 从独立 bootstrap 验证 root、可信时钟、最新版本及撤销新鲜度；有界严格解析 manifest、验 root 签名、角色、有效期及 allowlist。
2. 有界读取政策/契约精确字节，核对路径、版本和 allowlist；严格解析 ratification、验证域签名、key/角色、时间、A/B 和 Scope。独立核验原 claim 与 preparation/request，而非信任签名人声明。
3. 严格解析 baseline preflight，验证其 ratification hash、全部封闭字段、初始槽位和实际只读证据；重建 authority、CURRENT/EXPLICIT、root、checkpoint 与 runtime 预算。随后验证 live 签名、角色、有效期、精确 baseline preflight 和 ratification hash，以及全部逐字段绑定和确认。
4. 未来 R2 在同一 execution guard 下验证下表对应的实时阶段状态，并在每次转换前复查独立证据。预期的 decision/consumption 写入只改变对应实时槽位，不改变已签署的 baseline 字节或 hash；不得将实时槽位重建成另一个 preflight hash 来替换原授权。外部证据陈旧或改变与表中允许的本次单调转换不同，必须拒绝。每一步持久化需 no-clobber、文件及目录 fsync 与精确复核；不确定即停止。preflight/签名本身既不创建也不消费权限，验证不创建槽位、不修改原 claim 或 checkpoint。
5. dispatch 前在同一 guard 下重新核验原 claim 精确字节和 inode、authority/实际 CURRENT 或 EXPLICIT、所有 roots/result/parent、checkpoint 实际缺失、签名和受信 key 的有效期/撤销状态、runtime freshness 和预算、无关残留，以及表中预期的实时槽位。不得要求实时槽位仍与 baseline 的 ABSENT 相同。checkpoint 出现始终禁止生成，后续依 R0/R0D 审计。

| 阶段 | 允许的实时状态和转换 | 禁止状态或后果 |
| --- | --- | --- |
| baseline 签署及首次 decision link 前 | decision、consumption、terminal 均 ABSENT；checkpoint ABSENT；核验冻结 baseline 与独立证据。 | 预先存在 decision 仅供只读调查，DENY 新 invocation；不能用 `EXISTS_VERIFIED` 或旧 attempt ID 恢复。除非将来另行审查无循环绑定的 resumption 协议，否则不允许例外。 |
| decision 持久化并验证后 | decision 必须是本次 guard 内新写入、精确匹配且已持久化的记录，绑定原 baseline preflight hash、ratification 和 live envelope 精确 hash 及同一 attempt；consumption、terminal 和 checkpoint 仍 ABSENT。 | 不匹配、替换、额外记录或持久性不确定均 DENY；不能将已存在 decision 当作新的授权。 |
| consumption 持久化并验证后，dispatch 前 | decision 保持精确匹配；唯一 consumption 必须精确匹配并已持久化，引用该 decision identity 和同一 attempt；terminal 和 checkpoint 仍 ABSENT。仅同一连续受 guard 保护的操作在全部复核成功后可首次 dispatch。 | consumption 是单次使用点；出现或可能已出现后，任何异常、崩溃或持久性不确定均为已花费，禁止重新授权、恢复或重试，即使尚未发送网络请求。 |
| dispatch 后 | 不允许第二次消费或 dispatch；terminal 缺失为 outcome unknown，checkpoint 按既有审计规则处理。 | 任何重放、冲突或不完整状态 DENY 新 dispatch，不自动清理。 |

上述 decision 与 consumption 的专用绑定仍依赖下节 **OPEN DECISION** 所述未来 schema；现有 R1 不具备这些验证或 dispatch 能力。

## R1 实际来源与兼容边界

| 证据 | 当前实现及差距 |
| --- | --- |
| claim | `disposition_execution_claim.py` `_identity`/`_encoded` 定义 claim identity、preparation/window/request、snapshot 和 strategy；`inspect_claim` 不提供本提案完整 File 证据。claim 上限 16384。 |
| source/B1.2 | `disposition_resume.py` `_verify` 与 `disposition_preparation.py` 验证 session、selection；`disposition_recovery_audit.py` `_authority_hash` 绑定 snapshot、strategy 及 CURRENT/EXPLICIT。此处细化的 `Authority` 不是已有 R1 schema。 |
| checkpoint | `disposition_checkpoint_storage.py` `load_checkpoint` 验证精确槽位与 codec；缺失、损坏与不确定须区分。 |
| slots/root | `disposition_recovery_audit.py` 定义 v1 固定槽位与审计；`disposition_recovery_root.py` 有独立初始化 seam；`disposition_recovery_storage.py` 有 decision 持久化 seam。它们不提供审批认证或消费/dispatch API。 |
| runtime | `disposition_execution_claim.py` 要求调用者新鲜发现 runtime/tokenizer；session 自报不能证明新鲜。完整 `Runtime` 是新提案。 |

R1B3 `decision.policy_reference` 是自由文本，不是签名批准；R1B1 不验证签名。现有 decision 封闭字段没有这两个 envelope 和 preflight 的专用摘要绑定，不能假定支持新记录。未来 guarded R2 必须先验证完整签名和精确字节，逐项比对现有 decision 的 binding、roots、caps、reason、operator 和 attempt ID，再让 consumption 绑定经验证 decision identity 及同一 attempt。**OPEN DECISION**：通过新版本 decision/consumption schema 增加三个专用摘要，还是经另行版本化、封闭且不可歧义的绑定记录连接；在决定并审查迁移及审计前不得声称 v1 `evidence` 或 `policy_reference` 足以承载授权。预先存在的 decision 只能只读调查，不能用于新 invocation；同一 guard 内刚刚成功持久化的本次 decision 才可按阶段表继续。

## 失败矩阵（均 DENY dispatch）

| 条件 | 处理 |
| --- | --- |
| claim 字节/身份、incident、window/ordinal、preparation/request 或 source lineage 不匹配 | 拒绝；不能用自洽签名替代独立原始证据 |
| 签名有效但角色错误、key 过期/撤销、manifest 缺失/过期/回滚或时钟/撤销新鲜度不可信 | 拒绝；不能由 envelope 自建信任 |
| A/B reject、defer、缺失或与精确政策不匹配 | 拒绝；方向性同意不构成批准 |
| A6 或 B1.2 CURRENT 改变、EXPLICIT 选择或 strategy 不匹配 | 拒绝并重新核验；不能静默切换选择模式 |
| 有效 checkpoint 出现 | 禁止生成，按 checkpoint 优先及恢复审计处理 |
| root/parent/claim inode 或路径改变、初始化结果冲突 | 拒绝；不能采用替换 inode |
| 预先存在 decision、已消费、attempt 重放、terminal 或冲突记录、可疑临时残留 | 拒绝新 invocation；只读调查，不自动清理。同一 guard 内精确验证的本次 consumption 仅允许阶段表中的首次 dispatch |
| 损坏、无法验证、部分写入、link/fsync/锁或最终状态不确定 | 拒绝；不确定不是不存在 |
| 旧调用次数未知或假设剩余预算为零/任何数值 | 不推断剩余额度；无完整新增例外和独立授权则拒绝，即使有授权也只允许 Caps |
| runtime/tokenizer、预算、prompt/schema 或其他独立证据在 preflight 后改变 | 拒绝旧授权；只有槽位仍允许新 invocation 时才可重新冻结并独立签署，可能消费后禁止重试 |

未来纯 verifier 应以隔离合成标识与临时目录测试上述每行、重复键、非 canonical 字节、大小边界、跨 domain 签名及逐字段变化；不得把测试标识当 Alice 证据。`pyproject.toml` 已有 `rfc8785==0.1.4`，没有显式 Ed25519 依赖；未来实现可在独立审查后选择成熟审计库（如 `cryptography`），不得自制密码算法。确定测试向量、失败代码、签名库、配置证据 codec、bootstrap/角色及版本迁移均须独立审查；在 OPEN DECISION 解决前没有可用真实授权路径。
